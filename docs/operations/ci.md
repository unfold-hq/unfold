# CI and release workflows

When a run fails in a way this page does not explain, see [Troubleshoot CI and releases](ci-troubleshooting.md).

Unfold's CI, releases and publication run on GitHub Actions in [unfold-hq/unfold](https://github.com/unfold-hq/unfold) ([ADR-0055](../adr/adr-0055-github-unfold-hq-is-the-project-home.md)). The workflows live in [`.github/workflows`](../../.github/workflows/) and the local actions in [`.github/actions`](../../.github/actions/). Every job runs on a GitHub-hosted `ubuntu-24.04` runner, except the ARM64 leg of the release image build on `ubuntu-24.04-arm`, and every job's condition starts with `github.repository == 'unfold-hq/unfold'`, so the workflows do nothing in a fork or on a mirror. Every action is pinned to a commit and every image to a digest, no workflow names a Webgrip host or secret, and nothing pulls from Docker Hub ([ADR-0056](../adr/adr-0056-unfold-images-build-on-wolfi-and-ci-needs-no-docker-hub-account.md)). Every run and log is public: `gh run list --repo unfold-hq/unfold`, then `gh run view <run> --log-failed`.

## The pull request gate

The `gate` job of [on_pull_request.yml](../../.github/workflows/on_pull_request.yml) waits for every other pull request job except the advisory `agent-trace` and `warnings`, runs even when one of them failed, and succeeds only when each of them succeeded. Its check, `gate`, is the one the ruleset on `development` requires: a job added to the workflow joins the gate instead of a list of checks in the ruleset. The workflow also runs on `merge_group`, so the same jobs and the same `gate` run on the commit the merge queue builds from the pull request and the `development` it would land on; `agent-trace`, `release-notes` and `gitleaks` then read the range from `github.event.merge_group.base_sha` to `github.event.merge_group.head_sha` instead of the pull request's base and head ([repository requirements](#repository-requirements)). [The GitHub workflow policy test](../../scripts/github-workflow-policy.test.cjs) checks the gate's jobs and runs its script against passing, failed, cancelled, skipped and missing results.

`release-notes` is another. It runs `apps/unfold/scripts/changelog.ts require` from the pull request's base to its head: a `feat`, `fix` or `perf` commit, or a breaking one, that changes `apps/unfold` needs a release-note fragment in `apps/unfold/changes`, unless its scope is `deps`, `ploeg`, `ci`, `test`, `docs`, `release` or `site` or a commit carries the trailer `Release-Note: none` ([Write release notes](../../apps/unfold/docs/operations/release-notes.md)).

`gitleaks` is one of the jobs the gate waits for. It scans every commit between the pull request's base and head with the repository's [.gitleaks.toml](../../.gitleaks.toml), so a secret committed and removed again within the pull request still fails it, while findings in older history do not. It runs the gitleaks image that [the documentation scan](docs-publishing.md) pins, `ghcr.io/gitleaks/gitleaks` by digest, with no network and the checkout mounted read-only, so it reads no secret and needs no gitleaks-action licence. A manual run scans from `origin/development` to its head. When it fails, remove the value from every commit of the branch, rotate it if it was real, or allowlist a fixture path or a value shape that is never a secret in `.gitleaks.toml`.

## Shared checks and the Ploeg pin

Unfold depends on one release of [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg), pinned three times ([ADR-0039](../adr/adr-0039-unfold-depends-on-a-released-ploeg-through-its-contract-bundle-and-go-module.md), [ADR-0043](../adr/adr-0043-an-unfold-release-is-one-chart-that-carries-the-ploeg-it-was-tested-with.md)): [apps/unfold/ploeg-release.json](../../apps/unfold/ploeg-release.json) pins Ploeg's contract bundle `ghcr.io/ploeg-hq/ploeg-contract` by version and manifest digest, [the demo helper's go.mod](../../apps/unfold/scripts/unified-demo/go.mod) pins the Go module `github.com/ploeg-hq/ploeg` at the same version, and [the Unfold chart](../../apps/unfold/ops/helm/unfold/Chart.yaml) depends on the chart `ploeg` from `oci://ghcr.io/ploeg-hq/charts` at that version, locked in its `Chart.lock`. [scripts/ploeg-contract.py](../../scripts/ploeg-contract.py) `fetch` pulls the bundle anonymously, checks the manifest against the pinned digest and the layer against the manifest, and unpacks it into `apps/ploeg`, which Git ignores. `mise run setup` runs it, and so does every job that reads Ploeg's contract or documentation before it reads them. `check` fails when the pins name different releases, when `Chart.yaml` or `Chart.lock` names another `ploeg` release or registry, or when `apps/ploeg` holds another bundle; `mise run verify` runs it. The `ploeg-pin` job runs it with `--published`, which also requires the registry tag to still be the pinned digest, and the `release` job waits for it. A pull request that pins an unreleased Ploeg therefore stays red until Ploeg publishes it. `UNFOLD_PLOEG_CONTRACT_REGISTRY` points the fetch at a mirror; the digests make the source irrelevant. `chart` downloads the locked Ploeg chart into the chart's `charts/` directory, which Git ignores; `mise run setup` runs it, because `helm lint`, `helm template` and Unfold's chart tests need it even with `ploeg.enabled=false`. It pulls anonymously, with a throwaway registry configuration, so a stale `ghcr.io` login in a local credential store cannot refuse the public chart. Move all three with `mise run ploeg-pin 0.x.y-rc.N`, in a `fix(ploeg)` commit, which releases Unfold. It needs `go` and `helm`, which mise installs, and network access to `ghcr.io`: it writes `Chart.lock` with `helm dependency update` rather than by hand, because Helm refuses a lock whose digest of the requirements it cannot reproduce. Renovate leaves all three alone.

Source changes and pull requests use the same local [verification action](../../.github/actions/verify/action.yml) and [release-policy action](../../.github/actions/release-policy/action.yml). Each caller checks out the repository before invoking a local action. A pull request runs the release-policy action as its own job; the release train runs it as the first step of its `release` job. The application gates remain in [mise verification](../../scripts/verify.mjs), including generated docs, Helm goldens and deterministic integration. CI splits them over two jobs: `checks-unfold` runs the Unfold group, whose test suite is the longest gate, and `checks` runs every other group. `checks-unfold` installs with `mise run setup-unfold` instead of `mise run setup`: only the steps of `setup` that the Unfold group reads, which are the Ploeg bundle and chart, Unfold's tools and its npm packages. It restores no Go cache or pnpm store and installs no site, extension or docs dependencies. The action's `only` and `except` inputs set `UNFOLD_VERIFY_ONLY` and `UNFOLD_VERIFY_EXCEPT`, which name the groups a run keeps or leaves out. A third job, `build-contexts`, runs the [build-contexts action](../../.github/actions/build-contexts/action.yml): it builds both Unfold images from bases that pull without credentials ([ADR-0056](../adr/adr-0056-unfold-images-build-on-wolfi-and-ci-needs-no-docker-hub-account.md)) and holds each to its CVE budget with the [CVE gate](../../.github/actions/cve-gate/action.yml) the release runs, so a pull request from a fork builds them too.

Verification runs independent gate groups in parallel: Unfold, the AHP client run, the Unfold extension, the hosted demo replay, Ploeg, the site, Helm, release tests, integration and docs. The Ploeg group runs the pin check, its tests, and `go vet` and a build of the unified demo's Go helper against the pinned module. Unfold no longer runs Ploeg's own `scripts/verify.sh`; Ploeg's CI does. Gates inside a group stay sequential. Each gate's output is buffered and printed in group order with its result and duration, followed by a summary. The first failure cancels the running gates, skips the pending ones and names the failed gate. The managed qualification's embedded PostgreSQL starts on a port the operating system assigns, so checkouts can verify at the same time, and a server orphaned by a cancelled gate does not block the next run. The verification action restores the mise tool installs, the Go module and build caches, the npm download cache and the site's pnpm store from the GitHub Actions cache, and sets `GOFLAGS=-count=1` so Go never reports a cached test result. The mise key is the hash of the `mise.toml` and `mise.lock` files. On a miss the action restores the nearest older entry, mise installs only the tools that changed, and the result is saved under the new key. The Go key is the hash of the helper module's `go.sum` and its Go files, so a Ploeg bump or a helper change saves a fresh build cache and the next run restores the nearest one. The managed qualification's embedded PostgreSQL binaries, which the embedded-postgres library otherwise downloads from Maven Central on every run, are cached from `~/.embedded-postgres-go` under the library version in the helper module's `go.sum`; a Maven Central response other than 200 surfaces as `no version found matching <version>`, even for a version that exists. A pull request only restores these caches; saving them is left to `development` pushes, manual runs and the release train. The verified gate results are the exception: a pull request still saves them, so its next push reuses its passes.

Verification also keeps a result cache of gates that passed, in `~/.cache/unfold-verify`. A gate's key hashes the committed Git trees of its group's inputs, the root, Unfold and site `mise.toml` files and both verify scripts, the tool versions mise resolves in each scope, the `GOFLAGS` and `UNFOLD_TEST_TIMEOUT_SCALE` settings, the gate's command and the platform. A gate whose inputs have uncommitted or untracked changes gets no key. The Unfold group reads `apps/unfold` and `docs`, the AHP client and extension groups `apps/unfold`, the Ploeg group the pin file, the unified demo helper module and the pin check with its tests, the site group `apps/site` plus Unfold's `public`, `src`, `examples`, recorder and `package.json`, because its build records the demo replay and copies `public` into `/demo`, and the Helm group `apps/unfold/ops/helm`. Both pins live under `apps/unfold`, so the Unfold and Ploeg gates rerun when either moves, and the unpacked bundle, which Git ignores, never counts as an uncommitted change. The integration group reads `apps/unfold`, `scripts/integration.mjs` and `scripts/fake-litellm.mjs`. The release and docs groups span the whole tree and always run. Every CI run records its passes. Only a pull request reuses them (`UNFOLD_VERIFY_REUSE`): a push to `development`, the release gate, runs every gate. An npm update in Unfold therefore skips the Ploeg gates in its pull request. Outside CI, `mise run verify` uses `~/.cache/unfold-verify` and reuses its passes by default, so a gate whose committed inputs already passed on this machine is skipped. Set `UNFOLD_VERIFY_REUSE=false` to run every gate, or `UNFOLD_VERIFY_RESULTS` to use another directory, which then reuses only with `UNFOLD_VERIFY_REUSE=true`, as in CI. [The cache tests](../../scripts/verify-cache.test.mjs) state which changes keep a key and which change it. Markers unused for 14 days are removed.

`UNFOLD_VERIFY_CPUS` caps each gate's parallelism: it sets `GOMAXPROCS`, `go -p` and Unfold's `--test-concurrency`. Without it the tools start one worker per host core. CI sets 4, a starting value to tune against job duration. `UNFOLD_VERIFY_GROUPS` caps how many gate groups run at once; unset, all of them start together. Groups start in the order `scripts/verify.mjs` lists them, which is longest first as measured in CI (docs, site, integration, the AHP client run, the extension, then the short ones), so the two slots of the `checks` job do not end with one long group running alone. Every Node gate shares a V8 compile cache in the system temporary directory (`NODE_COMPILE_CACHE`, unless already set), so the test suite's 270 processes compile Unfold's modules once instead of each; it cut the suite's CPU time by about a third. Memory peaks with the number of groups running at once: measured on 2026-10-10 with warm caches, all ten groups at once peaked at 2.10 GiB (3.21 GiB cold), three at 1.79 GiB and two at 1.12 GiB, for 78, 71 and 90 seconds. CI sets 2. The Unfold test scripts also set `--test-timeout=120000` and `--test-force-exit`, so a test that never settles fails after two minutes instead of holding the runner until the job timeout.

## Warnings

GitHub Actions gives a job no warning result that holds a commit back, so a warning printed by a passing step would otherwise stay buried in a green log. The verification action therefore saves the output of its `mise install` steps, `mise run setup` and `mise run verify`, and its last step, which runs even after a failure, passes that output to [the warnings scanner](../../scripts/ci-warnings.mjs). The scanner recognizes the warning formats of npm, pnpm, mise, git and uv (both print a bare `warning:` line, so the report labels it `git or uv`), Node, Python, Go, Actions annotations and build tools, so a test name or a JSON log line that contains the word "warn" is not reported. It reports each distinct warning once and writes the list to its verification job's `warnings` output. A separate `warnings` job prints the lists of `checks` and `checks-unfold` and fails when either is not empty. The commit then shows a red `warnings` check while `checks` carries on and the release train still releases: the gate does not wait for `warnings`, and the train has none. Fix the cause, or accept a warning in [the allowlist](../../scripts/ci-warnings-allow.json) with a pattern and the reason it is accepted. A pull request that reuses cached gate results does not print those gates' output, so a push to `development` is the complete check.

The root `mise.lock` is committed. `min_version` in the root `mise.toml` refuses an older mise. Regenerate it with `mise lock`. Renovate relocks `mise.lock` itself when it bumps a tool.

The [browser flows](../../apps/unfold/scripts/browser-check.mjs) drive Unfold's deterministic demo in Chromium with Playwright. They run in [the browser suite action](../../.github/actions/browser-suite/action.yml) every night from [the nightly workflow](../../.github/workflows/on_nightly.yml), in Microsoft's Playwright image `mcr.microsoft.com/playwright` pinned by digest, and on command: dispatch that workflow, or run `mise run browser` locally. They do not run on a push. The image's tag must equal the `playwright` version in `apps/unfold/package.json`, because each Playwright release expects its own Chromium build; when Renovate moves one, move the other in the same pull request. CI sets `UNFOLD_BROWSER_TIMEOUT_SCALE` to 3, which triples each flow's default wait, and gives the job 45 minutes. Each flow logs when it starts and how long it took, so a run that hits the limit shows where it was. The browser flows gate no release and are not part of `mise run verify` or pull requests.

The AHP client run (`mise run ahp-e2e`, the `ahp-sdk` group of `mise run verify`) drives Unfold's deterministic demo with Microsoft's own client, [`@microsoft/agent-host-protocol`](https://www.npmjs.com/package/@microsoft/agent-host-protocol), and judges the host's state with the SDK's reducers. [The harness](../../apps/unfold/test/sdk-e2e/ahp-e2e.mjs) starts the demo on a free local port with an empty data directory and an environment stripped down to `PATH`, `HOME`, the temp directory and the locale, so no model key, provider URL or `.env` file reaches it. It refuses to run when the server does not report demo mode. It then connects as five profiles: VS Code 1.142 (offers `1.0.0, 0.10.0, 0.9.0`, sends `_meta["vscode.ahpSessionUris"]`, creates sessions on `ahp-session:/<uuid>`), VS Code 1.141 (`unfold:/<uuid>`, no `_meta`), a plain AHP client using the SDK's typed helpers, a version-negotiation probe and the SDK's multi-host layer. It prints one line per check, the failing ones with their evidence, and a pass count per profile; the wire logs and the full results go to a temporary directory it names. A whole run takes about 40 seconds. Every wait has its own timeout, a turn gets 90 seconds, and the run as a whole gets 240 seconds (`UNFOLD_AHP_E2E_TIMEOUT_MS`), each multiplied by `UNFOLD_TEST_TIMEOUT_SCALE`; when the budget runs out the run fails, kills the demo and exits. The SDK is an exact-pinned devDependency of `apps/unfold`, so Renovate moves it and the image never ships it.

[unfold-mcp's end-to-end suite](../../apps/unfold/test/e2e/mcp-over-https.e2e.ts) signs people in through a real Authentik and drives the HTTP MCP endpoint with the official MCP client ([what it checks](../how-to/serve-unfold-mcp-over-https.md#test-it-end-to-end)). [The nightly workflow](../../.github/workflows/on_nightly.yml) runs it every night and on command through [its action](../../.github/actions/mcp-e2e/action.yml), which starts Authentik and Postgres with the same Docker Compose file as `npm run test:mcp-e2e` locally. Its credentials are throwaway values for an instance that only the job reaches. Like the browser flows, it reports and gates no release, and it is not part of `mise run verify`, because Authentik takes about a minute to start. The suite's own readiness check waits up to four minutes for the health endpoint, the API and the default blueprints.

The weekly [demo smoke action](../../.github/actions/tutorial-smoke/action.yml) runs [the tutorial smoke script](../../scripts/tutorial-smoke.sh): it starts `mise run demo-unified`, waits for `unified-demo.ready`, stops it with `SIGTERM`, then runs the documented `--smoke` check. It is deterministic, with no model calls or credentials. When the runner has no PostgreSQL `initdb` and `postgres`, or runs as root, the job logs what is missing and passes without starting the demo. No release job depends on it.

The Unfold version is the application's ([ADR-0019](../adr/adr-0019-unfold-pins-ploeg-from-its-own-repository-and-releases-only-its-application.md), which supersedes the joint version of [ADR-0004](../adr/adr-0004-unfold-releases-one-version.md); [ADR-0039](../adr/adr-0039-unfold-depends-on-a-released-ploeg-through-its-contract-bundle-and-go-module.md) keeps it). Ploeg is versioned and published by [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg). The release job runs semantic-release from `apps`, so [the Unfold configuration](../../apps/.releaserc.cjs) applies. It loads the repository's own release configuration, [`scripts/release-config`](../../scripts/release-config/index.cjs), which defines the tags-only trains, commit rules and notes, files releases with `@semantic-release/github` and pins its toolchain in its own lockfile. The train is `unfold` (`monorepo: { name: 'unfold' }`), so only commits that touch a file under `apps/` count, and every commit in the release range must be a conventional commit or a merge (`ENONCONVENTIONAL` otherwise). Moving the Ploeg release touches `apps/unfold`, so its `fix(ploeg)` commit cuts the next Unfold candidate. The [marketing site](../../apps/site/README.md) lives under `apps/` but is not part of the Unfold version ([ADR-0012](../adr/adr-0012-the-marketing-site-releases-and-deploys-on-its-own.md)): a commit scoped `site` never releases Unfold, and neither train reads the other's tags. The configuration adds that rule after the shared rules and lowers the breaking rule from major to minor. The analyzer stops at the first major it finds, so a breaking rule left at major would release Unfold for a `feat(site)!` commit before the `site` rule is read. During 0.x `initialDevelopment` lowers a breaking change to minor anyway, and the release policy refuses 1.x. Its own train, [apps/site/.releaserc.cjs](../../apps/site/.releaserc.cjs), cuts `unfold-site-v…` releases; its `site-release` job runs after Unfold's `release` job in the release train, and the site's publication deploys it to Cloudflare, as the [site deploy guide](../../apps/site/docs/deploy.md) describes. Unfold's publication jobs accept only `unfold-v…` tags, so a site release publishes no image, chart or extension. A release is the tag alone: semantic-release tags the commit the train checked, `unfold-v<version>`, and files the notes as a draft GitHub release. The Unfold train's notes lead with the release-note fragments the release adds and fold the commit list below them ([scripts/release-notes-fragments.cjs](../../scripts/release-notes-fragments.cjs), [ADR 0072](../../apps/unfold/docs/adrs/0072-release-notes-are-written-per-change-and-the-workbench-shows-what-is-new.md)). It commits nothing, so `apps/CHANGELOG.md` (kept as the record of the notes before fragments), the chart, the manifests and the extension keep the version of the last release commit, `0.4.0-rc.114`. Publication sets the version: the chart and extension jobs run [the stamp script](../../apps/unfold/scripts/stamp-version.mjs) on their checkout of the tag before they package, the image build runs it on the application manifests, and `publish_chart.py` packages with `--version` and `--app-version` and refuses a packaged chart whose metadata differs from the stamped metadata at the release version. The release builds no VSIX before it tags: the train's `checks` package the extension (`extension:package` in `scripts/verify.mjs`) on the same head. The annotated tag `glide-v0.3.0` is the baseline where the last imported candidates met. Releases before the rename carry the old `glide-v` and `glide-site-v` names; when the product was renamed ([ADR-0013](../adr/adr-0013-the-product-is-named-unfold.md)), `unfold-v` and `unfold-site-v` baseline tags were placed on the same commits as the newest old tags, so the versions continue. Both source checks and release-policy checks must pass before versioning.

`UNFOLD_RELEASES_ENABLED`, a repository variable, must equal `true` to version or publish. A manual source-validation run never releases, even with the gate enabled; dispatch the release train instead. CI runs the import verifier with `UNFOLD_REQUIRE_IMPORT_NOTES=true`, so missing release-channel notes fail the check instead of being skipped as they are locally. A [release test](../../scripts/test_release_refs.py) fails if any workflow, action, script or mise task prunes, mirrors or deletes refs, or pushes notes. The [notes-loss record](../research/2026-09-23-forgejo-notes-loss.md) explains why. Keep the `main` release baseline; `development` remains trunk and the only automatic release branch.

## Agent Trace summary

The `agent-trace` job of a pull request says which lines of its commits an agent wrote. It fetches `refs/notes/agent-trace` from `origin` into the same local ref, without force, and goes on when `origin` has none. Then it runs the plugin's [report script](../../apps/unfold/extensions/claude-code/scripts/agent-trace-report.mjs) on the pull request's base and head commits and writes the Markdown to the job summary and the log. The notes reach `origin` when people push them, by hand or with the plugin's `UNFOLD_PUSH_AGENT_TRACE=1` ([how-to](../how-to/link-claude-code-sessions.md#show-reviewers-which-lines-an-agent-wrote)); no workflow pushes, prunes or deletes them. The job blocks nothing: every step ends in `|| echo`, no job needs it, and it is not a required context.

## Dependency updates

Renovate keeps Unfold's own managers and exceptions in [renovate.json](../../renovate.json). Minor, patch, digest and pin updates land in one `all non-major dependencies` branch and merge once [the gate](#the-pull-request-gate) is green. Unattended updates keep a soak of three days for a minor and one day for a patch. `internalChecksFilter: strict` leaves an unsoaked update out of the group, so it cannot hold the whole branch. Third-party majors and Go toolchain minors wait for a tick on the dependency dashboard. Ploeg is the exception: Ploeg's own release opens its pull request, described in [the next section](#the-ploeg-pin-pull-request). Renovate ignores mise's generated `.mise` lock directories. After it moves the pnpm that `apps/site/package.json` names, and after lock-file maintenance there, it runs `corepack pnpm install --lockfile-only` in that directory, so the lockfile's record of pnpm moves too ([Troubleshoot CI and releases](ci-troubleshooting.md)). Go keeps minor and patch apart, because combined Renovate would offer only the minor and the patch would never come; Go patches merge themselves in their own `Go toolchain patches` branch. The Mermaid and Marked pins of [the landscape build](../../apps/unfold/scripts/build-landscape.mjs) get a `landscape renderer` branch of their own: moving either makes [the landscape explorer](../landscape/explorer.html) stale, Renovate's runner has no Chromium to rebuild it, and in the shared branch that red gate held every other update back. The pull request says so; run `mise run landscape` on its branch and push.

The `opencode-contract` pull-request job runs `mise -C apps/unfold run opencode-contract`. It fetches the OpenCode build that [the agent image](../../apps/unfold/ops/agent/Dockerfile) pins, starts it against a local fake model that calls `grep`, and requires Unfold's OpenCode adapter to complete a turn with and without a permission round-trip ([test](../../apps/unfold/test/opencode-contract.test.ts)). An OpenCode update that breaks how Unfold reads or answers permissions therefore stays red. It runs on pull requests, including Renovate's, but not on a direct push to `development`. It installs only Node. `MISE_AUTO_INSTALL=false` keeps `mise exec` and `mise run` from installing the rest of the root `mise.toml`, Go among them. `agents-check` does the same with uv.

The `opencode-ai` rule names the package's source repository, because the npm package names none and Renovate otherwise puts no release notes in the pull request. The release notes are what a person merging reads first, and what a Run that explains the update reads: once the pinned Ploeg carries [Ploeg ADR-0109](https://github.com/ploeg-hq/ploeg/blob/development/docs/adrs/0109-a-pull-request-someone-else-opened-is-read-by-a-team-on-the-pull-request.md) and Unfold's repository is opted in, Ploeg's reviewer explains every Renovate pull request on the pull request itself, and the repository skill [explain-a-dependency-update](../../.agents/skills/explain-a-dependency-update/SKILL.md) tells it where each pin is used here. Until then that skill only serves a person or an interactive agent reviewing one.

Renovate opens a pull request as soon as it pushes a branch (`prCreation: immediate`). CI runs only on pull requests and on pushes to `development`, never on a `renovate/*` branch, so waiting for checks to pass first meant waiting for checks that never start: an update hung as a bare branch until the not-pending timeout.

`rebaseWhen: conflicted` rebases a Renovate branch only when it conflicts. With the preset's `behind-base-branch`, every push to `development` rebased every open Renovate branch, and each rebase started a full pull request run.

## The Ploeg pin pull request

When Ploeg publishes a release candidate and its contract bundle, Ploeg's release workflow opens the pin pull request itself ([ADR-0041](../adr/adr-0041-a-ploeg-release-opens-unfolds-pin-pull-request-by-running-unfolds-recipe.md), [Ploeg ADR 0127](https://github.com/ploeg-hq/ploeg/blob/development/docs/adrs/0127-a-release-opens-each-consumers-update-by-running-the-consumers-own-recipe.md)). Its `consumers` job clones `development`, runs [`scripts/consume-ploeg-release.sh <version>`](../../scripts/consume-ploeg-release.sh), commits what changed as `fix(ploeg): update Ploeg to <version>` on the branch `ploeg/<version>`, and opens the pull request with the `unfold-hq-bot` GitHub App in `by-consumer` mode, which leaves the merge to Unfold. [`on_ploeg_pin.yml`](../../.github/workflows/on_ploeg_pin.yml) runs [`scripts/release_train_pin.py`](../../scripts/release_train_pin.py) when such a pull request opens or moves: it turns on auto-merge for the newest pin at its head, and closes every older pin with a comment. The ruleset on `development` holds the merge until `gate` passes; with the merge queue on, auto-merge adds the pin to the queue once it is green. When the pin is already green, GitHub refuses auto-merge, and the script adds the pin to the merge queue at its head with the GraphQL `enqueuePullRequest` mutation and `expectedHeadOid`, so the queue's `gate` still runs before it lands; the script never merges a pin itself. Whether a merge the queue makes for a pull request `GITHUB_TOKEN` queued starts a push run was not observed yet; the next release train checks the head that holds it either way. The repository variable `PLOEG_PIN_AUTHOR` names the App's bot account when it is not `unfold-hq-bot[bot]`. The merge cuts the next Unfold candidate.

The recipe moves the three pins with `scripts/ploeg-contract.py pin`: the bundle's tag and digest in `apps/unfold/ploeg-release.json`, `github.com/ploeg-hq/ploeg` in the demo helper's `go.mod`, followed by `go mod tidy`, and the `ploeg` dependency of the Unfold chart, followed by `helm dependency update`, which rewrites `Chart.lock`. It then runs [`scripts/renovate-ploeg-docs.sh`](../../scripts/renovate-ploeg-docs.sh), which regenerates the decision register, Unfold's domain pages and the combined glossary from the new bundle, so a Ploeg release that adds an ADR arrives green. It installs Go, uv, Helm and Node from `mise.toml` on Ploeg's GitHub runner, which must reach `ghcr.io`, the Go module proxy, PyPI, the npm registry and Playwright's browser download. To move the pin by hand, run the same script, or `mise run ploeg-pin 0.x.y-rc.N` and then the regeneration.

Renovate no longer touches either pin: `renovate.json` disables both packages, so two writers never race on one file. `ploeg-docs` is one of the jobs [the gate](#the-pull-request-gate) waits for, so a pull request with a term clash cannot merge.

The [landscape explorer](../landscape/explorer.html) embeds the glossary, so a Ploeg release that changes the glossary also makes the explorer stale. The script rebuilds it when the machine has Node, Unfold's npm packages and Playwright's Chromium, so the recipe installs Node from `mise.toml`, runs `npm ci` in `apps/unfold` and installs Chromium before it pins. When that install fails, the recipe prints a notice and still pins, and the pull request needs `mise run landscape` from a person. Run 2291 (rc.57, 2026-10-24) is the failure this prevents.

The combined glossary cannot be regenerated when the new Ploeg model defines a term that Unfold's model also defines. The script then keeps the old glossary, writes the generator's explanation to `ploeg-glossary-conflicts.txt` at the repository root and exits 0, so the pull request still carries everything it could regenerate together with the report. The report never makes the pull request green: `scripts/docs.py --domain-check` fails while the report exists or the clash remains.

The `ploeg-docs` job runs that check (`mise run domain-check`) on every pull request. It covers the landscape explorer too, so `ploeg-docs` cannot pass while `checks` fails on a stale landscape. It then runs `scripts/docs.py --stage-only`, which resolves every documentation link without building the site, so a Ploeg release that moves or deletes a page's link target fails here as well: 0.2.0-rc.40 moved `pkg/worker/task.go` and broke four links that only `checks` caught. Both take seconds, because they skip the documentation build, so a broken pin shows as its own named red check instead of one more failure inside `checks`, and a pin pull request is safe to merge once `ploeg-pin` and `ploeg-docs` are green. `checks` runs the same check as part of `mise run docs-check`. When `ploeg-docs` fails, its log says which case applies:

- **A stale page** (`Stale generated domain view`, `Stale combined glossary`, a stale decision register, `Stale landscape`): run `mise run domain`, `mise run docs-decisions` and `mise run landscape` on the branch and push.
- **A missing link target** (`Missing documentation targets` naming a path under `apps/ploeg`): the new Ploeg moved or deleted a file an Unfold page links. Point the link at the file's new path in the bundle, or drop it, and push.
- **A term clash** (`Combined glossary conflicts`): two models define one term. Ploeg owns a term when Ploeg stores it or its API names it; otherwise Unfold owns it. The message names both models and suggests the owner. When Ploeg owns it, add the term to the Ploeg entry under `imports` in `docs/domain/model.yaml`, delete Unfold's copy, and move any clause that only Unfold meant into an Unfold term that links to it, as pull request #339 on the previous forge did for Tenant and Client. When Unfold owns it, Ploeg's model changes upstream instead. Then run `mise run domain`, delete `ploeg-glossary-conflicts.txt` and push to the `ploeg/<version>` branch.

The weekly `ploeg-ahead` job in [on_schedule.yml](../../.github/workflows/on_schedule.yml) unpacks the bundle of Ploeg's newest release (`scripts/ploeg-contract.py fetch-unpinned latest`) and, separately, a bundle built from the head of Ploeg's `development` with Ploeg's own `scripts/contract-bundle.sh build`, runs the same script with `UNFOLD_PLOEG_CONTRACT_UNPINNED=true` so it keeps that bundle, runs the same check without the landscape explorer (`--without-landscape`) and the same link check, and fails when a clash or a broken link would reach the next Ploeg pull request. Nothing opens an issue for it; the red scheduled run is the signal. The nightly `ploeg-behind` job in [on_nightly.yml](../../.github/workflows/on_nightly.yml) runs `scripts/ploeg-contract.py behind` and fails when GHCR lists a newer Ploeg release than the pin: a release whose pull request is still red, or whose `consumers` job never ran.

## The release train

Unfold is versioned by [on_release_train.yml](../../.github/workflows/on_release_train.yml), not by the push of a merge ([ADR-0046](../adr/adr-0046-an-hourly-release-train-versions-unfold-from-a-checked-development-head.md)). Pull requests merge minutes apart, and a release inside each push run would wait in a queue that grows with every merge.

The train starts when `[Workflow] On Source Change` passes on `development`, every hour at minute 7, and on command, only on `development` and only while `UNFOLD_RELEASES_ENABLED` is `true`. A push run that failed or was cancelled starts no train. The push trigger exists because GitHub dropped most scheduled runs; the schedule stays as a fallback for merges that start no push run, such as a Ploeg pin merged with `GITHUB_TOKEN`. Its concurrency group, `release-train`, is its own: a push run never cancels a train, a second train waits for the first, and GitHub keeps at most one waiting train, so a row of merges queues one.

1. `pending` checks out the branch head and runs [scripts/release-train.sh](../../scripts/release-train.sh) `pending`. It counts the commits since the newest `unfold-v` tag under `apps/` outside `apps/site`, and since the newest `unfold-site-v` tag under `apps/site`. When both are zero the train ends. A release adds a tag and no commit, so a release tag is on the commit it released and nothing after it is release output.
2. `checks`, `checks-unfold`, `build-contexts` and `ploeg-pin` run the push's jobs on that head. The verification action reuses no earlier gate result outside a pull request, so every gate runs.
3. `release` checks out the branch again, installs the release toolchain, runs the release-policy action, then `release-train.sh current <checked head>`: semantic-release runs only when the branch head is still the checked commit. When `development` moved during the checks, the job passes, versions nothing and says so, and the next train checks the newer head. When it cuts a release, it dispatches `on_release_published.yml` at the new tag. `site-release` repeats the head check and releases a site candidate after it.

A busy stretch with merges less than about 50 minutes apart therefore releases nothing until it ends. To release sooner, dispatch **[Workflow] On Release Train** on `development` once the last merge has landed.

A tag or release that `GITHUB_TOKEN` creates starts no workflow, but a `workflow_dispatch` does. So the job that cut a release runs `gh workflow run on_release_published.yml --ref <tag> -f tag=<tag>`, with `actions: write`. Dispatching at the tag is also what signs under the tag: the keyless identity is `https://github.com/unfold-hq/unfold/.github/workflows/on_release_published.yml@refs/tags/unfold-v0.x.y-rc.N`, issued by `https://token.actions.githubusercontent.com`, and the parse job refuses a dispatch whose ref is not the tag.

Unfold accepts only zero-major release candidates: a breaking change raises the minor version, and a `verifyRelease` guard in [scripts/release-policy.cjs](../../scripts/release-policy.cjs) refuses anything but `0.x.y-rc.N` from `development`. Publication runs for the same tag are serialized; a newer invocation does not cancel a partially completed publication.

## Publication

A chart in a registry is a complete release ([ADR-0043](../adr/adr-0043-an-unfold-release-is-one-chart-that-carries-the-ploeg-it-was-tested-with.md)), so publication of an `unfold-v…` tag runs in this order:

1. `unfold-release-build` builds each image for each platform on a runner of that platform, AMD64 on `ubuntu-24.04` and ARM64 on `ubuntu-24.04-arm`, so no QEMU emulation is needed. It switches the runner's Docker to the containerd image store, builds with Docker's own BuildKit, which attaches SLSA provenance, and pushes the platform image to `ghcr.io/unfold-hq` under a build tag such as `build-0.4.0-rc.132-amd64`, because Docker's own BuildKit cannot push by digest alone. The tag starts with `build-` so that it never reads as a version: a consumer's Renovate took the former `0.4.0-rc.134-arm64` for a newer release than the multi-platform `0.4.0-rc.134` and pinned an ARM64-only image. Nothing reads the build tag; the merge, the gate and the attestations use digests. No step pulls binfmt, a BuildKit image or BuildKit's SBOM scanner from Docker Hub. `unfold-release-images` then merges the two digests of each image into one index tagged with the version (`docker buildx imagetools create`), holds it to its CVE budget with the [CVE gate](../../.github/actions/cve-gate/action.yml), signs it keyless and attests its CycloneDX SBOM and CVE verdict, and attests a CycloneDX SBOM to each platform image. Both jobs ask GHCR first ([the probe action](../../.github/actions/ghcr-probe/action.yml)) and skip the build and the merge when the version is already published, so a retry signs what is there.
2. `unfold-release-publish-chart` needs that job, so a failed or cancelled image leaves no chart for the release. [scripts/publish_chart.py](../../scripts/publish_chart.py) receives the two digests, refuses a digest that is empty or that GHCR's tag no longer resolves to, and packages a copy of the chart whose defaults are each image at `ghcr.io/unfold-hq` with the release version and its digest. It runs `helm dependency build` first, so the package vendors the Ploeg chart that `Chart.lock` names, refuses a package that renders an Unfold image without a digest or carries another Ploeg chart, pushes it to `oci://ghcr.io/unfold-hq/charts/unfold` and signs it keyless.
3. `unfold-release-publish-extension` packages, verifies, signs and attests the VSIX, attaches it to the draft release and publishes it to Open VSX with Trusted Publishing ([Release Unfold](../../apps/unfold/docs/operations/release.md#extension-distribution)).
4. `unfold-release-distribute` runs [`scripts/publish_release.py`](../../scripts/publish_release.py), which verifies every artifact anonymously and against the keyless identity, attaches `release-artifacts-unfold.json` and takes the release out of draft without marking it latest.

For a site tag, `site-release-tag` decides the channel and `site-deploy-staging` or `site-deploy-production` deploys the site with `wrangler deploy` ([site deploy guide](../../apps/site/docs/deploy.md)). The [artifact guide](artifacts.md) lists the published identities and how to verify them. The Ploeg chart's own images are Ploeg's to pin.

## Release floors

[scripts/release-floors.json](../../scripts/release-floors.json) records, per application, the highest version any destination already holds (the floor), the versions above it that can never be used again, and the tag prefixes that have carried the application. Ploeg and Unfold both have the floor `0.4.0-rc.34`; Ploeg's withdrawn `1.0.0-rc.1` is still published and listed as never reusable. Ploeg's record is retired: no train may version Ploeg again, and the record keeps every version Unfold published for it, up to `0.4.0-rc.35`, out of reach. The [audit record](../research/2026-10-03-release-floors-and-identity.md) shows where each version lives.

The release policy's `verifyRelease` refuses a computed version that is at or below Unfold's floor, or at or below any existing tag under a prefix that has carried the application, such as `vloer-v` or `glide-v`. It lists every tag in the checkout, including tags a stale merge left unreachable from `development`, so a recomputed version stops before semantic-release tags anything. The Unfold publishers refuse a version at or below Unfold's floor before they read a registry or the forge, and refuse to publish Ploeg before any Git, network or file access. A retry of an existing release checks out its own tag and therefore keeps the floors it was cut with. [release_floors.py](../../scripts/release_floors.py) and [release-floors.cjs](../../scripts/release-floors.cjs) implement the same comparison and run the same [cases](../../scripts/fixtures/release-floor-cases.json). Raise a floor only with new audit evidence, and never lower one.

## Repository requirements

Proposed in [ADR-0061](../adr/adr-0061-development-merges-through-a-merge-queue-with-no-bypass.md). The workflows already support it; the owner applies the settings in the repository, which this repository cannot change. Until then the ruleset of [ADR-0055](../adr/adr-0055-github-unfold-hq-is-the-project-home.md) holds.

| Setting | Value |
| --- | --- |
| Ruleset target | `development` |
| Require a pull request before merging | on, with no required approvals |
| Require status checks to pass | `gate`, from GitHub Actions |
| Require merge queue | on, merge method **Merge commit**, so a Ploeg pin keeps its `fix(ploeg)` commit and the release ranges keep their merges |
| Bypass list | empty, administrators included |
| Block force pushes and deletion | on |
| Allow auto-merge | on, so [`on_ploeg_pin.yml`](../../.github/workflows/on_ploeg_pin.yml) can queue a pin that is not green yet |

`gate` is the only required check, on the pull request and in the queue alike: a job added to [on_pull_request.yml](../../.github/workflows/on_pull_request.yml) joins the gate, not the ruleset. A merge queue run that fails removes the pull request from the queue and leaves `development` untouched.

## Validation

Run `mise run verify` and `mise run release-check-github`. The latter runs the [release-policy tests](../../scripts/release-policy.test.cjs), [release-isolation tests](../../scripts/release-isolation.test.cjs) and [GitHub workflow policy tests](../../scripts/github-workflow-policy.test.cjs) with the repository's own release toolchain, then actionlint. They cover application-tag rejection, manual ref matching, disabled publication, CVE gates before signing, the single signing workflow, the absence of Ploeg publication, release floors and orphaned tags. Set `UNFOLD_RELEASE_HISTORY=true` to also compute the next version from the actual history and check it against the floors and the repository's tags; this needs a full clone. Passing workflow tests or a release preview does not prove publication; the [cutover playbook](first-cutover.md) lists the evidence a first release needs.

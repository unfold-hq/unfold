# Open WebUI: MCP client, license, governance (evidence, 2026-11-20)

Subject: [open-webui/open-webui](https://github.com/open-webui/open-webui) at tag [v0.13.4](https://github.com/open-webui/open-webui/releases/tag/v0.13.4) (published 2026-11-17), docs from [open-webui/docs](https://github.com/open-webui/docs) `main` as served at [docs.openwebui.com](https://docs.openwebui.com). Source was read through the GitHub API and the release tarball; nothing was run.

Abbreviation: `OW` = `https://github.com/open-webui/open-webui/blob/v0.13.4`. `SDK` = `https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0`.

## Summary

- The native MCP client is one file, [backend/open_webui/utils/mcp/client.py](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py). It wraps the official `mcp` Python SDK **2.3.0** (`Client` class, `mode='auto'`). That mode probes `server/discover` for 2026-07-28 and falls back to `initialize`, which offers 2025-11-25.
- Elicitation goes through the SDK's `elicitation_callback`. The SDK 2.3.0 `Client.call_tool` sends both legacy server-to-client `elicitation/create` requests and 2026-07-28 `InputRequiredResult` embedded requests through that one callback. So by code reading, a stateless JSON-only server that uses the InputRequired pattern **should** get the Open WebUI elicitation dialog. Two conditions apply: a browser socket session must be open on that chat, and the request must not time out. Nobody has tested this end to end; see Q1.
- MCP Apps arrived in v0.13.0. `_meta.ui.visibility` is honoured for both `model` and `app`.
- Auth modes: none, bearer, session, system_oauth ("OAuth"), oauth_2.1 (DCR) and oauth_2.1_static. Discovery uses RFC 9728 PRM, with WWW-Authenticate first and well-known URLs as fallback. PKCE is S256. The RFC 8707 `resource` parameter is sent by default (automatic, include or omit). Refresh is automatic. Tokens are stored Fernet-encrypted in the `oauth_session` table. **CIMD is not supported**: feature request [#26059](https://github.com/open-webui/open-webui/issues/26059) is open, and the source has no reference to it.
- MCP prompts: **not supported**, the client never calls `prompts/list` or `prompts/get`. MCP resources: used only for MCP Apps (`ui://` resources plus app-initiated `resources/read` and `resources/list`). They are never exposed to the user or model as attachable resources.
- License: BSD-3 plus a branding clause. Branding may be removed only with **≤50 end users per rolling 30 days**, written permission, or an enterprise license. It is not OSI open source. **Terminals and Tether ship under a separate proprietary "Open WebUI Enterprise License"**: production use needs a paid license, and Tether has a personal non-commercial exception.
- Governance: in the last 90 days on `dev`, `tjbck` (the founder) authored 1,358 of 2,794 commits (48.6%). The top 3 accounts authored 97.5%. There were 21 releases from 2026-07-01 to 2026-11-17.

The `initialize` fallback therefore offers **2025-11-25**, and the probe sends `server/discover` at **2026-07-28**.
- Probe logic, [SDK _probe.py `negotiate_auto`](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/_probe.py#L52): "Probes `server/discover` once ... then either `adopt()`s the result or falls back to `initialize()`."

[#33087]".
- Docs ([mcp.mdx](https://docs.openwebui.com/features/extensibility/mcp)): "Open WebUI connects to servers on the stateless `2026-07-28` protocol revision and on older revisions. It follows a redirect only when it stays on the same origin."

The client creates `streamable_http_client(url, http_client=..., max_sse_event_size=None)` ([client.py#L156](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L156)), so it accepts both JSON and SSE responses through the SDK transport.

### Elicitation

- Callback, [client.py#L87-L120](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L87-L120): `MCPClient.elicit(context, params)` validates the form schema with `Draft202012Validator.check_schema`, or for URL mode rejects non-http(s) URLs and URLs carrying userinfo. It then emits `{'type': 'request:elicitation', 'data': {mode, message, requested_schema, url, server_name}}` through `event_caller` and validates the answer against the schema ("Never fetch server-supplied schema references or coerce user answers."). Any failure returns `ElicitResult(action='cancel')`.
- The callback is wired only when a browser session exists, [tools.py#L266-L269](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/tools.py#L266-L269): `event_caller=extra_params.get('__event_call__') if metadata.get('session_id') else None`. Without a session the SDK default applies. [SDK session.py `_default_elicitation_callback`](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/session.py#L259) returns `ErrorData(code=INVALID_REQUEST, message="Elicitation not supported")`, and the elicitation capability is then left out ([session.py#L635-L637](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/session.py#L635-L637): `ElicitationCapability(form=..., url=...) if self._elicitation_callback is not _default_elicitation_callback else None`). Automations and API calls without a socket session therefore cannot elicit.
- UI: the socket handler treats `request:elicitation` as an input request with a timeout of `min(max(timeout_ms / 1000, 60), 240)` s, defaulting to 120 s and capped by `WEBSOCKET_EVENT_CALLER_TIMEOUT` ([socket/main.py#L1808-L1823](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/socket/main.py#L1808-L1823)). The frontend renders `ElicitationDialog` ([Chat.svelte#L6026](https://github.com/open-webui/open-webui/blob/v0.13.4/src/lib/components/chat/Chat.svelte#L6026)).
- Docs, "Requests for Your Input" ([mcp.mdx](https://docs.openwebui.com/features/extensibility/mcp)): "**Form requests** show a form with the fields the server asks for ... **Link requests** show a link to open ... The dialog waits up to 120 seconds, or `WEBSOCKET_EVENT_CALLER_TIMEOUT` when that is lower ... The dialog appears only while that chat is the one open in a browser tab; otherwise the request is cancelled at once."
- Version added: `client.py` has no `elicit` at v0.11.4 and has it at v0.12.0 (raw file grep per tag). The CHANGELOG has no entry that says "elicitation" explicitly. v0.12.4 ([CHANGELOG.md#L495](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L495)) mentions "an MCP server's input request".

### The decisive question: stateless JSON plus 2026-07-28 InputRequired

What the code shows:

1. Open WebUI calls tools through the high-level `Client.call_tool`, not `client.session.call_tool` ([client.py#L224](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L224): `result = await self.client.call_tool(function_name, function_args, read_timeout_seconds=tool_call_timeout)`).
2. In SDK 2.3.0, `Client.call_tool` runs the SEP-2322 multi round-trip driver automatically. [SDK client.py#L768-L772](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/client.py#L768-L772): "If the server returns an `InputRequiredResult`, the embedded input requests are dispatched to this client's sampling / elicitation / roots callbacks and the call is retried automatically (up to `input_required_max_rounds`)." The default is `DEFAULT_INPUT_REQUIRED_MAX_ROUNDS = 10` ([_input_required.py](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/_input_required.py)).
3. The dispatch routes "each embedded request through the same callback table that serves legacy server→client RPCs, so the two paths stay behaviourally identical by construction" ([SDK client.py#L916-L919](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/client.py#L916-L919), via `session.dispatch_input_request`).
4. So an `InputRequiredResult` carrying an elicitation input request reaches `MCPClient.elicit`, which shows the same `ElicitationDialog`. The answer goes back in a retried `tools/call` that carries `input_responses` and `request_state`. No SSE stream is needed for this path.

Conclusion from the code: **yes, a stateless JSON-only 2026-07-28 server asking for confirmation through InputRequired should get the Open WebUI form**, provided that:

- the server answers `server/discover` with `2026-07-28` in `supported_versions`, so the connection adopts modern mode (a JSON-only server that also accepts `initialize` gets legacy mode, which does not change this path because `InputRequiredResult` handling depends on the negotiated version); see the unknowns below;
- the tool call runs from a chat that is open in a browser tab, so a `session_id` exists;
- the user answers within roughly 60–240 s.

Unknown or not verified:

- No end-to-end test observed. Nobody has run Open WebUI against such a server, and no Open WebUI test for InputRequired was looked for. `grep -i input_required` in the Open WebUI backend matches nothing; the support comes from the SDK only.
- Whether `InputRequiredResult` is accepted when the connection fell back to the `initialize` handshake (legacy era) was not traced in `ClientSession.call_tool`.
- `MCPClient.elicit` takes `isinstance(params, ElicitRequestFormParams)` as the form case and treats any other value as URL mode. Whether the 2026-07-28 embedded elicitation params deserialize to the same `ElicitRequestFormParams` type was not checked.
- The OAuth PRM probe ([oauth.py `get_protected_resource_metadata`](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L431)) POSTs a bare JSON-RPC `initialize` with `params: {}` to find the `WWW-Authenticate` header. A modern-only server that rejects `initialize` without a 401 header falls back to the well-known URIs, so this should still work, but it has not been tested.
- The client connection is opened per chat-completion request, and per app RPC in [routers/tools.py#L332-L365](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/routers/tools.py#L332-L365), which calls `connect_mcp_server` and then `client.disconnect()` in a `finally`. Server-side sessions therefore do not outlive a request. This fits a stateless server.

## 2. MCP Apps

- Added in **v0.13.0** ([CHANGELOG.md#L349](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L349)): "🧩 **MCP Apps in chat.** Tools from MCP servers that come with an interactive app now show that app right in the chat after they run, in a sandboxed frame that can only reach the sites the server declares, and every tool call the app wants to make waits for you to confirm it." v0.13.1 added "📮 **MCP Apps message the chat.**" ([#L229](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L229), [#33907](https://github.com/open-webui/open-webui/pull/33907)).
- Backend: [apps.py](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/apps.py). It has `APP_MIME_TYPE = 'text/html;profile=mcp-app'` and `MAX_APP_BYTES = 5 * 1024 * 1024`. The resource URI is read from `_meta.ui.resourceUri` or the legacy `_meta["ui/resourceUri"]` and must start with `ui://`. The CSP is built from `resourceDomains`, `connectDomains`, `frameDomains` and `baseUriDomains`. Callbacks are bound per server and tool with an HMAC over `WEBUI_SECRET_KEY` ("A stable WEBUI_SECRET_KEY is required for MCP apps").
- Frontend: [MCPApp.svelte](https://github.com/open-webui/open-webui/blob/v0.13.4/src/lib/components/chat/Messages/MCPApp.svelte) uses `AppBridge, PostMessageTransport` from `@modelcontextprotocol/ext-apps/app-bridge`. An app-initiated `tools/call` requires `requestConfirmation($i18n.t('Tool call'), ...)` ([#L111-L121](https://github.com/open-webui/open-webui/blob/v0.13.4/src/lib/components/chat/Messages/MCPApp.svelte#L111-L121)).
- The client advertises the extension `io.modelcontextprotocol/ui` with `mimeTypes: ['text/html;profile=mcp-app']` ([client.py#L163](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L163)).
- **Visibility is honoured.** [client.py#L384-L388](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L384-L388) defines `tool_visible_to(tool, visibility)` with default `['model', 'app']`. `list_tool_specs` skips tools that are not visible to `'model'` ([#L199](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L199)). The app RPC proxy refuses app calls to tools that are not visible to `'app'`: "Tool is unavailable to this app" ([routers/tools.py#L351-L354](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/routers/tools.py#L351-L354)). The origin tool must also be model-visible: `if not origin or not ui_resource_uri(origin) or not tool_visible_to(origin, 'model')` → 403. Docs: "A tool's `_meta.ui.visibility` decides who can use it: a tool without `model` is hidden from the model, and a tool without `app` cannot be called by apps." The visibility code first appears at v0.13.0 (grep count 0 at v0.12.4, 3 at v0.13.0).
- App-to-host methods the proxy allows: `Literal['tools/call', 'resources/read', 'resources/list', 'ui/resource']` ([routers/tools.py#L294](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/routers/tools.py#L294)). Apps send messages to the chat as text only (docs).

## 3. Auth modes for MCP connections

Code: [tools.py `build_tool_server_headers`](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/tools.py#L150-L184), which handles `auth_type` values `'bearer'`, `'session'`, `'system_oauth'`, `'oauth_2.1'` and `'oauth_2.1_static'`. Tether servers use `'none'`.

Docs ([mcp.mdx, Authentication Modes](https://docs.openwebui.com/features/extensibility/mcp)):

- **None**: "Use this for **local MCP servers** or internal networks where no token is required."
- **Bearer**: "Use this **only** if your MCP server requires a specific API token."
- **Session**: "Sends the user's own Open WebUI session token as a bearer token."
- **OAuth** (`system_oauth`): "Sends the access token from the user's Open WebUI SSO sign-in as a bearer token." In code it uses `OAuthTokenAuth`, which resolves the token per request and retries once on 401 when the token rotated ([client.py#L54-L74](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L54-L74)).
- **OAuth 2.1**: "Uses Dynamic Client Registration (DCR)." Code: `get_oauth_client_info_with_dynamic_client_registration` ([oauth.py#L570](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L570)).
- **OAuth 2.1 (Static)**: "Uses a pre-created client ID/client secret." Code docstring ([oauth.py#L686-L695](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L686-L695)): "Build an OAuthClientInformationFull from user-provided static credentials. Performs server metadata discovery to resolve authorization/token endpoints, but skips dynamic client registration entirely." It uses `client_secret_post`, or `client_secret_basic` when that is the only method listed. Public clients (`token_endpoint_auth_method: none`) are not supported: open feature request [#34216](https://github.com/open-webui/open-webui/issues/34216).

Discovery (both OAuth 2.1 modes):

- RFC 9728: [oauth.py `get_protected_resource_metadata`](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L431-L507). It POSTs `initialize`, reads `resource_metadata=` from `WWW-Authenticate`, and otherwise falls back to `/.well-known/oauth-protected-resource{path}` and then `/.well-known/oauth-protected-resource` ("Fall back to well-known resource metadata URIs (RFC 9728 §4.2)"). It takes `resource`, `authorization_servers` and `scopes_supported` from the document.
- AS metadata: `_build_well_known_urls` tries `oauth-authorization-server{path}`, `openid-configuration{path}`, `{path}/.well-known/openid-configuration`, then the root variants, for each authorization server and then the MCP URL ([oauth.py#L511-L533](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L511)). If nothing is found and the PRM named no AS, it falls back to `/authorize`, `/token` and `/register` per MCP 2025-03-26 ("MCP 2025-03-26 defines origin-level defaults for servers without discovery.").
- Static can point discovery at a separate **OAuth Server URL** (docs, step 7).
- PKCE ([oauth.py#L951-L964](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L951-L964)): "Default to S256 for OAuth 2.1 (PKCE is mandatory per RFC 9700)" and "Only remove PKCE if metadata explicitly excludes S256".
- RFC 8707: `build_oauth_request_params` adds `params['resource'] = client_info.resource` when `should_send_oauth_resource` ([oauth.py#L803-L829](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L803-L829)). The mode is `omit`, `include`, or automatic, where automatic skips it when a scope already carries a resource indicator. The resource is also sent on token exchange (`token_kwargs['resource']`, [#L1357](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L1357)) and on refresh (`refresh_data['resource']`, [#L1223](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L1223)). Docs: "forwards it as the `resource` parameter on the **authorization redirect**, on the **token exchange**, and on every **refresh-token call**."
- Scopes: PRM `scopes_supported` or a custom list. Docs: "Use discovered scopes (default) ... Custom scopes".
- Refresh: proactive, within 5 minutes of `expires_at` ([oauth.py#L1164-L1177](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L1164-L1177)). A failed refresh deletes the session; per the docs, temporary provider errors keep it. **Known gap**: a 401 from the MCP server does not trigger a refresh. Open bug [#34699](https://github.com/open-webui/open-webui/issues/34699) (2026-11-19, v0.13.4): "Every MCP request gets `401 invalid_token` ... and makes no refresh request to the token endpoint."
- Token storage: table `oauth_session`, Fernet-encrypted with `OAUTH_SESSION_TOKEN_ENCRYPTION_KEY` ([models/oauth_sessions.py#L21-L85](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/models/oauth_sessions.py#L21)). The token is stored per user and per client id `f'{connection_type}:{oauth_server_id}'` ([tools.py#L176-L178](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/tools.py#L176-L178)). Docs: "the access they grant is stored against their account alone. Nobody else inherits it." Docs warning: without a stable `WEBUI_SECRET_KEY`, OAuth MCP tools break on restart with "Error decrypting tokens".
- **CIMD: not supported.** No match for `client_id_metadata`, `client-id-metadata` or `cimd` in `backend/` or `src/` at v0.13.4. Feature request [#26059 "feat: CIMD support"](https://github.com/open-webui/open-webui/issues/26059) is OPEN (opened 2026-06-15) and states: "Right now only Dynamic Client Registration (DCR) or static OAUTH is supported."
- Limits: MCP servers are admin-only on the instance (docs: "Regular users cannot register them on the instance, by design"). Users add personal ones through Tether. OAuth 2.1 tools cannot be model defaults (docs: "requires an interactive browser redirect").

## 4. MCP prompts and resources

- **Prompts: not supported.** No call to `list_prompts`, `get_prompt` or `prompts/list` exists in `backend/`; the only `get_prompt*` hits are Open WebUI's own prompt library in `routers/prompts.py`. `MCPClient` has no prompt methods ([client.py](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py)).
- **Resources: only for MCP Apps.** `MCPClient.list_resources`, `read_resource` and `read_ui_resource` exist ([client.py#L294-L347](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L294-L347)). Their only caller is the app RPC proxy ([routers/tools.py#L332-L359](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/routers/tools.py#L332-L359)). There is no UI for users to browse or attach server resources, and no resource subscription. Embedded `resource` and `resource_link` content inside tool results does reach the chat (CHANGELOG [#L2252](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L2252): "Tool results that return resource content — including binary blobs and URI references — are no longer silently dropped").
- Other capabilities: server `instructions` are appended to the system prompt (docs, "Server Instructions"). `structuredContent` is appended as JSON text unless it duplicates the text content. `outputSchema` is ignored (`# TODO: handle output_schema if needed`, [client.py#L206](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L206)). Sampling and roots callbacks are not passed to `Client`, so the SDK defaults apply (not supported).

## 7. Adjacent features (one line each)

- **Tether**: proprietary desktop app (macOS, Windows, Linux) that ties a user's computer to Open WebUI over an outbound connection, carrying local models, local and stdio MCP servers, OpenAPI tools and Open Terminal. "Commercial or organizational production use requires an Open WebUI Enterprise License" ([docs/ecosystem/tether](https://docs.openwebui.com/ecosystem/tether)). Introduced v0.13.1 (CHANGELOG [#L204](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L204)). In v0.13.4 it also relays MCP ([tether.py](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/tether.py): "Commands, endpoints and credentials stay on the device").
- **Terminals ("a computer for every user")**: proprietary orchestrator that provisions [Open Terminal](https://github.com/open-webui/open-terminal) (MIT) containers per user, chat or model, or shared. "An instance can belong to a user, a chat or a model, or be shared by everyone, with its own files, processes, packages, resource limits, network profile and optional persistent storage" ([docs/features/open-terminal/terminals](https://docs.openwebui.com/features/open-terminal/terminals/)). v0.13.4 CHANGELOG [#L15](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L15): "**A computer for every user.** With Terminals 0.4.0 or later connected, Open WebUI now hands out sandboxed computers on demand". It requires an Enterprise License for production. It also runs coding agents (Claude Code, Codex, ACP agents) as chat models (CHANGELOG [#L16](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L16)).
- **Channels**: "persistent, shared spaces where humans and AI models participate in the same conversation" ([docs/features/channels](https://docs.openwebui.com/features/channels/)). External "Apps" can join channels, added in v0.12.1 (CHANGELOG [#L705](https://github.com/open-webui/open-webui/blob/v0.13.4/CHANGELOG.md#L705)).
- **Notes**: "a dedicated workspace for content that lives outside of any single conversation ... a note reaches the model as its full text" ([docs/features/notes](https://docs.openwebui.com/features/notes/)).
- **Knowledge**: RAG knowledge bases. "Upload your files, attach the knowledge base to a model or conversation, and ask a question" ([docs/features/workspace/knowledge](https://docs.openwebui.com/features/workspace/knowledge)).

## Follow-up

### F1. Redirect URI for OAuth 2.1 (Static)

- Template: `{webui.url or request.base_url}/oauth/clients/mcp:{connection_id}/callback`. From [oauth.py#L697-L699](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L697-L699):
  > `webui_url = await Config.get('webui.url')`
  > `redirect_base_url = (str(webui_url or request.base_url)).rstrip('/')`
  > `redirect_uri = f'{redirect_base_url}/oauth/clients/{client_id}/callback'`
- `client_id` here is the internal key `f'{type}:{form_data.client_id}'` ([routers/configs.py#L194-L196](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/routers/configs.py#L194-L196)). The frontend sends the **Connection ID** as `client_id` with `type='mcp'` ([AddToolServerModal.svelte#L130-L141](https://github.com/open-webui/open-webui/blob/v0.13.4/src/lib/components/AddToolServerModal.svelte#L130-L141): "client_id is the tool server ID (used as the internal lookup key for both flows)"). The registered URI is therefore, for example, `https://chat.example.com/oauth/clients/mcp:my-server/callback`. The path contains a literal colon, and the IdP's redirect-URI allowlist must accept it.
- Routes: `@app.get('/oauth/clients/{client_id}/authorize')` ([main.py#L2929](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/main.py#L2929)) and `@app.get('/oauth/clients/{client_id}/callback')` ([main.py#L2975](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/main.py#L2975)).
- Base URL: env var `WEBUI_URL` ([config.py#L1687](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/config.py#L1687): `WEBUI_URL = os.getenv('WEBUI_URL', '')`). It is stored as config key `'webui.url'` ([config.py#L3255](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/config.py#L3255)). When empty, the request's `base_url` is used, which behind a proxy may be wrong. The docs require the authorization to finish "at the address in `WEBUI_URL`" ([mcp docs](https://docs.openwebui.com/features/extensibility/mcp)).
- The Connection ID must not change after registration (UI toast: "Save the connection to keep the OAuth details. Keep the Connection ID unchanged.").

### F2. Scopes when "OAuth Scopes" is empty (Static)

- [oauth.py#L708-L714](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L708-L714):
  > `scope = (' '.join(oauth_scope.replace(',', ' ').split()) if oauth_scope else None) or (' '.join(resource_metadata.scopes_supported) if resource_metadata.scopes_supported else None)`
- So the order is: the admin's custom scopes, then **PRM (RFC 9728) `scopes_supported`**, then `None`, meaning no `scope` parameter is sent (`build_oauth_request_params` adds `scope` only `if client_info.scope`, [oauth.py#L826-L827](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L826-L827)).
- Static mode does **not** fall back to the AS `scopes_supported`. The DCR path does: [oauth.py#L607-L608](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L607-L608), `if oauth_client_metadata.scope is None and oauth_server_metadata.scopes_supported is not None: oauth_client_metadata.scope = ' '.join(oauth_server_metadata.scopes_supported)`.
- The `WWW-Authenticate` `scope=` hint is not read; only `resource_metadata=` is parsed ([oauth.py#L456-L459](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L456-L459)).

### F3. offline_access and refresh tokens

- `offline_access` is **not** added automatically. `grep -i offline` in [oauth.py](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py) matches only the Google special case at [#L830-L833](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L830-L833): "Google only issues a refresh token for offline access ... `params['access_type'] = 'offline'`; `params['prompt'] = 'consent'`". That applies only when `authorization_endpoint.host == 'accounts.google.com'`.
- The client metadata declares `grant_types=['authorization_code', 'refresh_token']` ([oauth.py#L732](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L732)), which is declarative only for a static client.
- A refresh token is used when the AS returns one. Without one, the session is treated as expiring and the user must re-authorize: "No refresh token available for session" ([oauth.py#L1199-L1200](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/oauth.py#L1199-L1200)). If an AS issues refresh tokens only for `offline_access`, put it in PRM `scopes_supported` or in the admin's custom scopes.

### F4. clientInfo sent to the server

- Open WebUI passes no `client_info` to `Client(...)` ([client.py#L161-L166](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/mcp/client.py#L161-L166) passes only `transport`, `extensions`, `read_timeout_seconds` and `elicitation_callback`). There is no `client_info` or `Implementation` anywhere in `backend/open_webui/utils/mcp/`.
- The SDK default applies: [SDK session.py#L67](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/session.py#L67) `DEFAULT_CLIENT_INFO = types.Implementation(name="mcp", version="0.1.0")` and [#L424](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/client/session.py#L424) `self._client_info = client_info or DEFAULT_CLIENT_INFO`. The server therefore sees `{"name": "mcp", "version": "0.1.0"}`. How the SDK carries client info in the 2026-07-28 per-request envelope was not traced.
- HTTP headers: when `ENABLE_FORWARD_USER_INFO_HEADERS` is on, user-info headers plus chat and message id headers are added ([tools.py#L191-L197](https://github.com/open-webui/open-webui/blob/v0.13.4/backend/open_webui/utils/tools.py#L191-L197)).

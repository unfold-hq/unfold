# VS Code 1.145 to 1.147 against Unfold: the client got stricter with third-party hosts

Research date: 2026-11-18. This dossier follows [the 1.144 dossier](2026-10-29-vscode-1-144-fit.md) to the [1.147 release](https://code.visualstudio.com/updates/v1_147) of 2026-11-18. It also covers [1.145](https://code.visualstudio.com/updates/v1_145) (2026-11-04) and [1.146](https://code.visualstudio.com/updates/v1_146) (2026-11-11), which had no dossier. It asks what the three releases change for Unfold's Agent Host Protocol (AHP) host, its VS Code extension, its Agent Plugin and its MCP servers, what they newly make possible, and what the protocol and plugin specifications did around them.

Sources:

- the release notes of 1.145, 1.146 and 1.147;
- `microsoft/vscode` at tags 1.144.0 (`2c33b50b`), 1.145.0 (`a717861c`), 1.146.0 (`69047191`) and 1.147.0 (`8a14f0cc`), each checked out and diffed, plus the `product.json` of an installed 1.147.0;
- the [AHP repository](https://github.com/microsoft/agent-host-protocol) through its release of 1.1.0, the [Agent Plugins specification](https://github.com/agentplugins/agent-plugins-spec) and GitHub's changelog from 2026-10-29 to 2026-11-18;
- this repository at `origin/development` `e9f1255e`, with Ploeg pinned at 0.2.0-rc.112.

**Method.** Four research agents ran in parallel: one on the ecosystem, two on the agent-host client (1.144 to 1.146, and 1.146 to 1.147), and one on the extension and policy surface. The claims that drive a verdict were then re-checked first-hand in the trees: the history check before a send, the annotations channel, the reconnect on system sleep, the host's own `reconnect` answer, `chat.workspaceRemoteAgentHosts`, the policy counts, the enforcement of `vscode.allowedHarnesses`, the Inbox rule, the visual renderers and their fence names, the one-time automation flag, the Agents-window capability order, and on GitHub the AHP 1.1.0 release, Agent Plugins [#89](https://github.com/agentplugins/agent-plugins-spec/pull/89) and AHP [#603](https://github.com/microsoft/agent-host-protocol/pull/603), [#604](https://github.com/microsoft/agent-host-protocol/pull/604) and [#612](https://github.com/microsoft/agent-host-protocol/pull/612). Evidence read in code is marked **(source)**; everything else rests on documentation or changelogs. Nothing was run against Unfold's host.

**Landing.** This dossier, an [ADR 0012](../adrs/0012-agent-host-protocol-host.md) update, a dated sentence on the AHP paragraph of the [protocol ledger](2026-09-11-ecosystem-alternatives.md#appendix-adjacent-components-and-communication-protocols) and the [watchlist](2026-10-13-protocol-integration-gaps.md#watchlist) (thirteen rows updated, T49 to T52 added). ## Verdict

For the first time since the host shipped, a release changes how the client treats a host that advertises nothing. Two changes in 1.147 can stop a person's message or review comment from reaching Unfold, and neither is in the release notes. Around them, the three releases open one new surface worth a spike, settle three open questions from the 1.144 dossier, and leave the policy risk where it was.

1. **A person's message can now fail on a history check.** **(source)** Before a send, 1.147 compares the host's turns with the requests in its own chat model. If the host has a turn after the last one the client knows, the client first asks the host to truncate, waits for the answer, and on a refusal shows "Chat history could not be restored: …" and does not send. 1.146 made a narrower request, did not wait for the answer, and sent the message anyway. Unfold always refuses to truncate, because a transcript is evidence. The likely way in is a reconnect: 1.147 newly closes the connection when the computer sleeps, Unfold answers every `reconnect` with snapshots, and the client rebuilds its chat history only on two other events. A Round that finishes while a laptop sleeps is the ordinary case for a Work Item session. Not observed in a running VS Code yet.
2. **The first review comment can lose its channel.** **(source)** Until 1.146 the client derived the annotations channel as the session URI plus `/annotations` for every host. 1.147 derives it only for VS Code's own host and otherwise reads `annotations.resource` from the session summary or state. Unfold publishes that field only once a session has comments, and never in the summary. A session without comments therefore has no channel in 1.147.
3. **Nothing else breaks, and the host already tolerates the rest.** **(source)** The client still offers `1.0.0, 0.10.0, 0.9.0` and subscribes only `ahp-root://`. Every new `vscode.*` flag is opt-in. New unasked traffic is a `flowControl` offer on each `subscribe` (1.146), `_meta` on `chat/inputCompleted` (1.147), more keys in `root/configChanged`, and two attachment shapes. With the multi-harness setting on, the client offers `1.1.0` first (1.145) or `1.2.0` first (1.147), and the host answers the highest offer in its 1.x range. Of all this, only the extra `subscribe` options are pinned in a test.
4. **Editor windows can attach to Unfold.** **(source)** Since 1.145 the setting `chat.workspaceRemoteAgentHosts` lets an ordinary editor window connect to WebSocket agent hosts and list their sessions in the Chat view, in trusted workspaces only. Until now VS Code listed Unfold's sessions only in the Agents window; an editor window shows them only in the extension's own views. An entry holds an address, a name and an optional connection token, so a repository cannot declare its host without a secret in the file, but the extension can write the entry for the person.
5. **Visual answers are open to any host, behind two switches that are off.** **(source)** In the Agents window, a fenced `vscode-ui` block renders as metrics, badges, tables and bar charts, and a fenced `html-preview` block as sanitised HTML, for every session provider. Both settings default to off, and a client with them off shows the block as source code. A Work Item's spend and checks fit the component set; the host cannot yet tell whether a client renders them.
6. **Send Later, drafts and Inbox mode stay on the client.** **(source)** Send Later is a one-time automation that the remote provider switches off in code, so no host can opt in. A draft lives in client storage and replays its saved configuration days later, which the host re-validates. Acknowledging a session is client-side, and the session returns to the Inbox when its status bits or `modifiedAt` change.
7. **Managed settings still do not reach Unfold.** **(source)** `vscode.allowedHarnesses` (1.147) governs only VS Code's local Claude and Codex harnesses. The policy file has 64 entries and none names remote agent hosts; `chat.remoteAgentHostsEnabled` is still a plain setting. One thing did tighten: since 1.147 an organisation that sets MCP access to none also removes every third-party extension's chat tools, which includes Unfold's three.
8. **The extension no longer needs a setting to run in the Agents window.** **(source)** Since 1.145 the manifest's `capabilities.agentsWindow.supported` is honoured unconditionally. Views and walkthroughs are not drawn there, so what remains in that window is commands, tools, the MCP server, the URI handler and webview panels.
9. **AHP 1.1.0 is released.** It was tagged on 2026-11-13 and carries per-chat providers, per-chat configuration, a TCP channel and windowed delivery (both experimental), changeset file status and `environment.pathStyle`. `main` is already 1.2.0 with one-time automation triggers and run targets, the protocol shape of Send Later. VS Code honours per-chat providers for every agent host behind a setting that is off by default.
10. **The Local harness goes away in February 2027, and Unfold does not depend on it.** **(source)** Extension tools are published as client tools to every agent-host session type, remote hosts included; chat participants are not supported outside Local, and Unfold has none.

## What the three releases are

- **1.145 (2026-11-04).** Browsing through a remote agent host, remote canvases, mixed harnesses in one session, cron schedules for local automations, inline attachment pills, a managed MCP allow-list that takes precedence, organisation-required plugins, and the Timeline API finalized.
- **1.146 (2026-11-11).** The Local harness deprecated and the Copilot harness the default, Inbox mode, inline actions in the session list, chat windows, extension management in the Agents window, Skills over MCP, environment variables masked in the sandbox, and a managed setting that also blocks standalone canvas extensions.
- **1.147 (2026-11-18).** Send Later, drafts, sharing a remote as a GitHub Environment, Inbox acknowledgements and scope pickers, model routers, HTML previews and native visuals, guided automation creation with end dates, instructions for the assisted-permission reviewer, screenshots of other apps and image mark-up, browser use, remote HTML files in the integrated browser, sandbox retries with scoped file access, `vscode.allowedHarnesses`, and regular expressions in managed shell rules.

**(source)** `vscode.d.ts` changed once, in 1.145, for the Timeline API. The proposal list went from 185 to 187: `notificationTelemetry`, `contribChatResources`, `contribTitleBar` and `structuralDiff` were added, `timeline` was finalized and `github` was deleted. The installed 1.147.0 grants none of the new proposals to a third-party extension.

## The agent host client, changed in source

**(source)** The baseline is unchanged: `SUPPORTED_PROTOCOL_VERSIONS` is `['1.0.0', '0.9.0']` with `0.10.0` as the legacy offer, and the only initial subscription is `ahp-root://`. `PROTOCOL_VERSION` moved from `'1.1.0'` to `'1.2.0'` in 1.147, and the vendored protocol pin from `1d639930` (1.144) to `d7a5579b` (1.145, 1.146) to `f1f4d4ac` (1.147).

New host-advertised capabilities. A host that advertises none of them is still correct. Unfold advertises only `vscode.ahpSessionUris` and `vscode.autonomousAutomations`.

| --- | --- | --- | --- |
| `InitializeResult.multipleChatProviders` | 1.145 | A chat names its own provider; needs `chat.agentHost.multipleChatProviders.enabled` and the host's root config echo | Spike: recommendation 9 |
| `InitializeResult.tcpConnections` | 1.145 | Browsing through the host, remote canvases, and since 1.147 remote HTML files, over `createTcpConnection` and `ahp-tcp:/` | T15, T44 |
| `vscode.automationHistory` and two siblings | 1.145 | `vscode/deleteAutomation`, `vscode/acknowledgeAutomationDeletion` | No; the catalogue is read-only |
| `vscode.managedWorktrees`, `vscode.forceWorktreeCleanup` | 1.145 | Listing and removing managed worktrees | No |
| `vscode.sideChatWithoutContext` | 1.146 | A side chat without source context | No |
| `vscode.sandboxCertificate.refresh` | 1.146 | `vscode/refreshSandboxCertificate` | No |
| `vscode.githubEnvironment` | 1.147 | Registering the host as a GitHub Environment | No |
| `vscode.scheduledChatExistingConversation`, `AutomationCapabilities.oneTime` | 1.147 | Send Later; the remote provider sets `supportsOneTimeAutomation: false` | Closed to remote hosts; T51 |
| `vscode.prepareSessionWorktreeCleanup` | 1.147 | `vscode/prepareSessionWorktreeCleanup` | No |

What reaches a host that advertises nothing:

- **1.145.** URIs of the host's own files arrive as `file:///…` instead of `vscode-agent-host://…`. With inline attachments on, a pill becomes a Markdown link inside the message text. The client reads `SessionSummary.origin` from remote hosts, may resend a `subscribe` lost to a reconnect, and may send one `unsubscribe` too many.
- **1.146.** Each non-root `subscribe` carries a `flowControl` offer; a plain `snapshot` answer is accepted. The client stops re-listing sessions after a turn and relies on `root/sessionAdded`, `root/sessionRemoved` and `root/sessionSummaryChanged`, which the host sends. It answers a `ping` request from the host. `root/configChanged` gains keys, among them the person's instructions for the assisted-permission reviewer.
- **1.147.** The history check and the annotations change of the verdict. `chat/inputCompleted` carries `_meta['agentHost.inputResponseSource']` when a person answered. A skill reference arrives as a `resource` attachment with `displayKind: 'skill'`, and a plain string or URL as a simple attachment. A rejected credential at connect ends the connection with "Authentication failed. Reconnect to sign in again." and no retry. The client reads `InitializeResult.environment.pathStyle` and no longer asks `getNetworkDiagnosticsInfo` for the host's platform. `chat.agentHost.experimental.prewarmSessions` now defaults to on, so opening the composer creates a provisional session on the host.

**(source)** `setClientManagedSettingsPermissions` still goes to every host, with an empty document for any host that is not VS Code's local one. Regular-expression rules and `vscode.allowedHarnesses` never travel in it.

## Deep dives

### The history check before a send

**(source)** In `agentHostSessionHandler.ts`, 1.147 collects the ids of the chat model's requests before the one being sent, finds the last of the host's turns with one of those ids, and when later turns exist dispatches `chat/truncated` through `dispatchConfirmed`, which waits for the host's own envelope. A `rejectionReason` becomes the error "Chat history could not be restored: {0}", and the turn is never dispatched. 1.146 looked only at the request directly before the new one, did nothing when the host did not know that request, and never waited for an answer.

The client learns of a turn in three ways: from the snapshot when a session opens, from a turn it sent, and from a host turn it sees while that turn is active. It rebuilds its history from the host's turns on only two events, a `chat/turnsLoaded` action and a change in context usage. It does not listen for a snapshot applied after a reconnect.

**(source)** Unfold's [host](../../src/ahp/host.ts) answers `reconnect` with `{ type: 'snapshot', snapshots }` for every channel, and refuses `chat/truncated` in every kind of session. On a Work Item the reason reads "A Work Item is Ploeg's record and is read-only in the Agents window. Act on it from its Work Item page.", which after VS Code's prefix tells a person who only typed a note nothing they can act on. 1.147 also closes the transport when the operating system suspends and reconnects on resume. So the path is: a Work Item's chat is open, the computer sleeps, Ploeg finishes a Round, the computer wakes, the client reconnects and receives a snapshot with the new turns, and the next message the person types needs a truncation the host refuses.

Three things are not established: whether a reconnect replaces the session handler, which would rebuild the history; whether a snapshot reaches the chat model by another route; and whether a turn the host starts and completes in immediate succession is always seen while active. The first step is therefore a reproduction. The candidate fixes, none chosen:

- replay the actions a client missed when it reconnects, so each new turn is seen while active, and fall back to snapshots only past a retention window;
- after a reconnect snapshot, give the client the event on which it rebuilds its history;
- keep refusing, with a sentence that tells the person to reopen the session.

Accepting the truncation is not a candidate, because it would delete evidence or pretend to.

**Update 2026-11-19.** Reproduced at protocol level, not yet in a running VS Code. A client that keeps its chat model as 1.147 does (`agentHostSessionHandler.ts` lines 3027 to 3060, 3088 to 3140 and 3877 to 3909) is asked to truncate and refused after a reconnect, on a Work Item session whose Round finished while it slept and on an Unfold session another window wrote in. The host now follows each reconnect snapshot of a chat with an empty `chat/turnsLoaded`, the second candidate: the client's reducer adds no turn for it (`channels-chat/reducer.ts` line 804), and the session handler rebuilds its history from the turns it holds. A deliberate edit of an earlier message is still refused, and a Work Item now says that it keeps every Round. The cases are in [the 1.147 tests](../../test/ahp-vscode-1-147.test.ts) and [the Work Item tests](../../test/ahp-work-items.test.ts).

The refusal sentence is now shown to the person, where VS Code 1.142 dropped it. A person who deliberately edits an earlier message or restores a checkpoint in an Unfold session gets an honest answer in 1.147, where 1.146 sent the message as if the history had been cut.

### The annotations channel

**(source)** `getSessionAnnotationsResource` returns `session.annotations?.resource`, and only for a host that identifies as VS Code's own falls back to the session URI plus `/annotations`. The feedback path uses it through `getFeedbackAnnotationsChannel`, and the session cache fills `annotations` from the session summary, the session state and summary changes.

**(source)** In [review.ts](../../src/ahp/review.ts), `annotationsSummary` returns nothing while a session has no comments, and only `sessionState` includes it; `summary` never does. The fix is to publish `annotations: { resource, annotationCount: 0, entryCount: 0 }` in both for every session that can be reviewed. AHP 1.1.0 documents the channel as `ahp-annotations:/<uuid>`; a client that reads the advertised resource does not care about its spelling, so the existing spelling can stay. What the feedback UI does without a channel is not verified. The host also accepts comments carried inside a message, so the first comment may still arrive that way.

### Editor windows and a host a workspace names

**(source)** `chat.workspaceRemoteAgentHosts` is a window-scoped, restricted setting: an array of `{ address, name, connectionToken? }`. Its description says editor windows connect to these hosts while the workspace is open, that their agents become available in Chat and their sessions are listed there, that editor windows do not use `chat.remoteAgentHosts`, and that it applies only in trusted workspaces. It also warns that connected hosts receive the person's GitHub credentials. Unfold's agents declare `protectedResources: []` and its `authenticate` stores nothing.

Unfold accepts a connection token as a bearer header or as the `tkn` query parameter ([upgrade-auth.ts](../../src/ahp/upgrade-auth.ts)). A repository that committed this setting would commit a person's token, which the secret rule forbids. A window-scoped setting can also be set at user level, which is where the extension already writes `chat.remoteAgentHosts`. The spike question is whether the extension can add the same entry there, so the Work Items a person follows appear in the Chat view of the window they code in. Not verified: whether a user-level value is honoured, and whether the editor's composer draws the host's required configuration.

### Drafts and provisional sessions

**(source)** A draft is stored in the profile under `sessions.savedDrafts.revision.<uuid>`. Saving or deleting one sends nothing. Reopening one disposes the composer's current provisional session, calls `resolveSessionConfig` once or twice, the second time with the saved values, and creates a new provisional session with them. The values can be days old. [session-config.ts](../../src/ahp/session-config.ts) already answers `resolveSessionConfig` with defaults for anything it no longer offers and refuses `createSession` with a plain sentence, so a removed Team or a budget above the limit cannot start work.

The client's `disposeSession` is best-effort, and a comment in the client expects the host to collect empty sessions. Unfold's host keeps provisional sessions in a map with no limit and no expiry; its idle sweeper covers only ended sessions. With pre-warming on by default, every opened composer now leaves one. AHP [#612](https://github.com/microsoft/agent-host-protocol/pull/612), a draft opened on 2026-11-18, would give draft sessions their own lifecycle (T52).

### Inbox mode

**(source)** A session's Inbox state is kept in the profile. `getSessionInboxActivity` is the string `status:updatedAt:lastTurnEnd`, and both times come from the summary's `modifiedAt`. An acknowledged session returns when that string differs from the one stored, or when an input request appears that was not acknowledged. Republishing an identical summary, or changing only the activity text, the title or a read flag, does not return it.

For a Work Item session, `modifiedAt` is Ploeg's `updatedAt`. Whether Ploeg moves that time on changes a person does not need to see is not established, so the desktop pass checks it. To learn what a needs-input session waits for, the client's attention service loads the chat of every such session, which means a `subscribe` and its history per waiting Work Item.

### Native visuals and HTML previews

**(source)** The Agents window's chat view sets `renderHtmlPreviews` and `renderNativeComponents` for every provider. A block renders once its closing fence has arrived, when `chat.htmlPreview.enabled` or `chat.nativeComponents.enabled` is on; both are off by default.

- **`vscode-ui`.** Components are `Stack`, `Columns`, `Text`, `Metric`, `Badge`, `Table` with `Column`, `Row` and `Cell`, `BarChart` with `Bar`, and `Disclosure`. Limits are 32,000 characters, 100 rows, 12 columns and 24 bars. An unknown component or attribute rejects the whole block, and the person sees the source with the reason. The definition is `nativeComponents.ts` with its parser, and the built-in `vscode-ui` skill documents it.
- **`html-preview`.** Up to 64,000 characters, sanitised to basic markup, inline styles, a fixed SVG subset and base64 images. Scripts, forms, links and external resources are removed.

A Work Item's budget and spend as metrics, its checks as a table and its Rounds as a bar chart fit. Two things stand in the way. A client with the setting off shows raw source, which is worse than today's plain sentences. And the host has no signal for what a client renders. The extension runs in the Agents window and already registers its window with the host, so it could report the two settings there. That is the spike.

### Send Later and one-time automations

**(source)** `remoteAgentHostSessionsProvider.ts` sets `supportsOneTimeAutomation: false`, and three guards check it before the host's capabilities are read. The wire shape is `automation/createRequested` with one `oneTime` trigger carrying `runAt`, which AHP merged for 1.2.0 in [#603](https://github.com/microsoft/agent-host-protocol/pull/603), and a target that sends each run's message into one existing chat, from [#604](https://github.com/microsoft/agent-host-protocol/pull/604). Neither is released. For Unfold the equivalent would be "follow up on this Work Item at nine": a note Ploeg holds until a time. That is a Ploeg contract, and no one has asked for it (T51).

### Policy and managed settings

**(source)** `thirdPartyAgentEnabledValue` in `copilotManagedSettings.ts` is attached only to the settings that enable VS Code's local Claude and Codex harnesses. The remote provider's `_isAgentDisabledByPolicy` returns false. `policyData.jsonc` holds 63 policies at 1.144 and 1.145 and 64 from 1.146, the addition being `UpdateRestartWhenIdle`. No policy names `chat.remoteAgentHosts*`.

What an organisation can switch off in Unfold, as of 1.147:

- the Agents-window and editor connections, through no policy of their own: only the general switches that turn off AI features or agent mode reach them, and `chat.remoteAgentHostsEnabled` is a setting the person controls;
- the extension's three chat tools, with `chat.extensionTools.enabled` or, new in 1.147, by setting MCP access to none;
- `unfold-mcp`, with the MCP allow-list or the deny-list;
- the Agent Plugin, with the marketplace restrictions (`strictKnownMarketplaces`, `ChatExtraMarketplaces`, `ChatPluginsEnabled`).

An organisation can also require the plugin, through `enabledPlugins` (1.145), and since 2026-11-18 a team on GitHub can make it a default.

### The extension in the Agents window

**(source)** `canExecuteOnSessionsWindow` checks the person's `extensions.supportAgentsWindow` setting, then the product allow-list, then the manifest's declared `capabilities.agentsWindow.supported`. At 1.144 the declaration counted only with an experimental setting. The installed 1.147.0 lists 28 extensions on its allow-list and Unfold is not one, which no longer matters. The sessions window has no Activity Bar and draws no contributed view container, tree view or walkthrough, so of the extension's surface only commands, the three tools, the MCP server definition, the URI handler and the webview panels can work there. The context key `isSessionsWindow` is available to `when` clauses without a proposal. The workspace file name the extension uses to recognise the window, `agent-sessions.code-workspace`, is still in the tree.

Two small effects: an open Unfold panel keeps `retainContextWhenHidden`, which blocks the idle update restart of 1.146 on machines that turn it on; and the new `--hidden-window` flag would let extension-host tests run without a window, which the extension does not have yet.

### Plugin links

**(source)** `vscode://chat-plugin/install?source=…&plugin=…` accepts a GitHub shorthand, an `http`, `https` or `ssh` URL with a host, or the `user@host:path.git` form, plain or base64. That was already so at 1.144. 1.147 rewrote the handler: it takes an optional `harness=copilot|vscode`, needs no open chat, and refuses in remote and web windows. A plugin's MCP server keeps its OAuth client id only in VS Code's own MCP client; an agent-host session does not receive it.

## AHP and Agent Plugins

### Agent Host Protocol

- **Released.** 1.1.0 on 2026-11-13: per-chat providers and configuration, `chat/moved`, `ChangesetFile.status` in place of `isEditing`, changeset nonces, `environment.pathStyle`, `ToolCallResult.resultMetadata`, byte ranges on `resourceRead`, skills as children of an MCP server customization, `authenticate.target` and `accountId`, and two experimental channels: windowed delivery and TCP. Steering and queued input merged into `queuedMessages`. The restriction that a client may send only user messages was removed ([#551](https://github.com/microsoft/agent-host-protocol/pull/551), closing [#542](https://github.com/microsoft/agent-host-protocol/issues/542)), with no authorization added. The compatibility baselines stay `1.0.0` and `0.9.0`.
- **Unreleased, 1.2.0.** One-time automation triggers and automation targets.
- **Open.** Draft sessions ([#612](https://github.com/microsoft/agent-host-protocol/pull/612)), session artifacts ([#508](https://github.com/microsoft/agent-host-protocol/pull/508), a draft since 2026-10-08), a canvas registry (#528), model sources (#543) and a proposal for output directories (#609). The canvas read path [#545](https://github.com/microsoft/agent-host-protocol/pull/545) was closed for [#561](https://github.com/microsoft/agent-host-protocol/pull/561): a host should serve reads of the URIs it publishes.
- **Who implements it.** The Servers list gained AgentConnect on 2026-11-03. No other commercial vendor is listed, and Unfold is not on it.

**(source)** None of the 1.1.0 renames touches what Unfold's host emits: it publishes neither `isEditing`, `steeringMessage` nor a canvas.

### Agent Plugins specification

Portable hooks ([#89](https://github.com/agentplugins/agent-plugins-spec/pull/89)) merged on 2026-11-13 into the 1.1.0 working draft: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse` and `Stop` in `hooks.json`, with tool profiles for MCP, shell, file and web. The draft still says it "defines no OAuth configuration". There is no 1.1.0 release.

### Around them

- **Skills over MCP** shipped in VS Code 1.146 as a preview. The MCP client matrix does not list VS Code under Skills yet.
- **GitHub** documents Claude and Codex as its only third-party coding agents and no way to become one.
- **Publishing.** Azure DevOps postponed the retirement of global personal access tokens from 2026-12-01 to 2027-01-27. Since the move to GitHub ([ADR-0055](../../../../docs/adr/adr-0055-github-unfold-hq-is-the-project-home.md)) the release workflow publishes to Open VSX with trusted publishing, so the reason for T47 is gone.

## Recommendations

All behaviour below is proposed. Items 2 to 5 and 12 are small builds, 1 starts with a reproduction, 6 is a pass a person runs, 7 to 9 are spikes, 10 is documentation, and 11 is a Ploeg decision.

1. **Reproduce the history check, then close it.** Attach a client that behaves as 1.147 does, let a Work Item's transcript gain a turn across a reconnect, and send a message. If the client asks to truncate, choose between replaying missed actions on reconnect and giving the client the event on which it rebuilds its history. Never truncate.
2. **Advertise the annotations channel on every session that can be reviewed**, in the summary and the state, with zero counts before the first comment.
3. **Pin what the three releases send unasked.** One test file, as for 1.144: an offer that starts with `1.2.0`; `flowControl` on `subscribe`; `_meta` on `chat/inputCompleted`; a `root/configChanged` with the reviewer instructions, which is echoed to its sender only and neither stored nor logged; skill and URL attachments and `file:` URIs; a client-sent turn with a non-user origin, which is still the signed-in person's message; and a duplicate `subscribe` and `unsubscribe`. Return `environment: { pathStyle: 'posix' }` from `initialize`.
4. **Expire provisional sessions.** A limit per person and an expiry for a provisional session nobody sent a message in.
5. **Tell the person when an attachment did not reach the Team.** A message with an image or a file attached is forwarded as text today. Say so in the reply.
6. **Run the desktop pass on 1.147.** It settles what source reading could not: the history check, the first review comment, an acknowledged Work Item in the Inbox, a Work Item that appears without a reload, what the extension offers in the Agents window, and the plugin link.
7. **Spike Work Items in the editor window's Chat view** through `chat.workspaceRemoteAgentHosts`, written by the extension at user level.
8. **Spike a Work Item's spend and checks as native visuals**, shown only to a client whose extension reports that it renders them.
9. **Spike per-chat providers.** The 1.144 dossier said to advertise `multipleChatProviders` once 1.1.0 was cut. The question is narrower now: does naming each Run chat's harness show a person anything, without offering them a harness picker that the Team's Roles already decide?
10. **Document what an organisation's policies do to Unfold.** The page covers the four switches above, the allow-list entry `unfold-mcp` needs, the plugin as the route that survives strict estates, and the install link.
11. **Carry three approval rules into [Ploeg ADR 0100](../../../ploeg/docs/adrs/0100-an-attended-run-relays-its-harnesss-requests-through-ploegd-and-falls-back-to-its-teams-policy.md) before it is accepted.** How long a person's approval lasts and that it never widens the sandbox; whose request it is when no person started the Run; and whether a Team may give an advisory judge its own guidance in plain language.
12. **Move the Marketplace token date** in the release workflow and [the release guide](../operations/release.md) to 2027-01-27.

The decisions these leave for the owner: which fix closes item 1 once it is reproduced; whether to run spikes 7, 8 and 9 (7 is recommended, 8 and 9 can wait); whether Skills over MCP waits for VS Code to appear in the client matrix (recommended); and whether a dropped attachment should later become a Ploeg context file.

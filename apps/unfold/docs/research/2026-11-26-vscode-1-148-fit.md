# VS Code 1.148 against Unfold: what was built still stands, two host defects surface, and an extension can now register the host

Research date: 2026-11-26. This dossier follows [the 1.147 dossier](2026-11-18-vscode-1-147-fit.md) and [the maximal-integration dossier](2026-11-19-vscode-1-147-maximal-integration.md) to the [1.148 release](https://code.visualstudio.com/updates/v1_148) of 2026-11-25. For Unfold's Agent Host Protocol (AHP) host, its VS Code extension, its MCP servers and its Agent Plugin it asks: what does 1.148 break or put at risk, what can Unfold newly use, what stays closed, and what is already queued for 1.149. The owner's decision of 2026-11-19 stands: Unfold integrates with VS Code as far as it can, unless a surface would spend or execute outside Ploeg.

## Verdict

1. **Nothing in 1.148 breaks what Unfold built on 1.147.** **(source)** The client still offers `1.0.0, 0.10.0, 0.9.0` and subscribes only `ahp-root://`. The annotations channel, the session-artifact keys, the changeset channel and the five client gates of the earlier upstream drafts are unchanged. All eight proposed-API typings that Unfold Insiders vendors are byte-identical to 1.148.0. The 1.147 trap that could stop a message after a reconnect is closed in the client itself: 1.148 rebuilds its chat history on every change of chat state.
2. **A reconnect fails as a whole when one subscribed channel no longer exists.** **(source, probe)** Unfold answers `reconnect` and `initialize` by subscribing each requested channel in turn, and one error fails the request. The client then retries ten times over about three minutes before it starts over. The composer of a new session keeps a subscription to its provisional session, and Unfold keeps provisional sessions in memory, so every restart of the host can cost a person with an open composer three minutes without Unfold. The client logic is the same as in 1.147; neither earlier dossier found it.
3. **1.148 pages chat history, and Unfold answers the page request with nothing.** **(source)** A chat state that carries `turnsNextCursor` now makes the client call `fetchTurns` when a person scrolls to the top or runs Find. Unfold sets that cursor on a history cut at 200 turns, a build of the last round, and answers `fetchTurns` with an empty result and no `chat/turnsLoaded`. Older turns cannot be loaded and Find reports an incomplete search. It is not in the release notes.
4. **An extension can now register an agent host, and Unfold Insiders already does.** **(source)** The proposed API `chat.registerRemoteAgentHost` is new in 1.148. On 1.148 and later, Unfold Insiders keeps the connection token in memory and writes no setting, the host gets a row in Remote Environments with a Troubleshoot page, and every editor window that runs the extension connects to the host and lists its sessions in Chat. That settles a spike of the 1.147 dossier without a workspace setting, for Unfold Insiders only.
5. **Native visuals are on by default.** **(source)** `chat.nativeComponents.enabled` and `chat.htmlPreview.enabled` default to `true` in 1.148, so a Work Item's spend, checks and Rounds can be drawn as metrics, tables and bar charts. The host cannot see which VS Code it talks to, because the client's `clientInfo` carries a name and a title and no version, and a 1.147 client still shows such a block as source code.
6. **The five features the notes lead with are built for machines, and none reaches Unfold.** **(source)** Keeping a machine awake, cleaning up worktrees, creating Dev Containers, sandbox profiles and password prompts each need a capability, a root configuration schema or a host kind that Unfold does not have, and each would execute outside Ploeg. Two of them carry an idea worth taking to Ploeg.
7. **An agent in another session still cannot start work on Unfold.** **(source)** The experimental Dev Container hand-off also publishes tools that create sessions on connected remote hosts. They refuse a host whose root state does not advertise `vscode.remoteSessions`, which Unfold never does.
8. **MCP in the workbench is unchanged; three things around it moved.** **(source)** An MCP App can go fullscreen, and Unfold's card stays inline only because it declares `inline` alone. In Copilot sessions a new major version of the Copilot SDK talks to `unfold-mcp`, with a protocol version nobody can read from the tree. VS Code and Claude Code now appear under Skills in the MCP client matrix, which fires a watchlist trigger while Unfold's `mcp.skills` flag is still off.
9. **AHP moves on after 1.1.0, and one change needs an answer before 1.149.** On AHP's `main`, deferred turns replace the paging that verdict 3 is about, and `authenticate` gains an OpenID Connect ID token that VS Code's `main` already forwards. Unfold's host answers `authenticate` with success for any resource, including one it never advertised.
10. **What stays out is what would spend or execute outside Ploeg.** Dev Containers, worktree clean-up, sandbox profiles chosen in a client, a server update method, the TCP channel, a person's own model keys, auto-fix and auto-merge on a pull request, and remote delegation stay refused, for the reasons the earlier records gave ([ADR-0002](../../../../docs/adr/adr-0002-ploeg-is-the-only-engine.md), [ADR 0023](../adrs/0023-unfold-submits-work-to-ploeg-and-never-executes-it.md)).

## Deep dives

### A reconnect that names a channel the host lost

**(source)** After a transport drop the client opens a new connection and sends `reconnect` with every channel it is subscribed to. When the host answers that it does not know the client, the client sends `initialize` with the same channels as `initialSubscriptions`. Any other error fails the attempt (`platform/agentHost/browser/agentHostProtocolClient.ts:1355-1440`). Attempts repeat after 1, 2, 4, 8 and 16 seconds and then every 30, ten in all, which is 181 seconds (`platform/agentHost/common/reconnectPolicy.ts:29-34`). After the tenth the client closes for good and the service builds a new connection from scratch, whose first `initialize` subscribes only the root channel (`platform/agentHost/browser/remoteAgentHostServiceImpl.ts:817-843`). During those three minutes every request and action for that host waits behind the reconnect.

**(source)** Unfold's host answers both commands with a loop that subscribes each channel and returns the snapshots, so one unresolvable channel fails the whole request ([host.ts:1624](../../src/ahp/host.ts#L1624), [host.ts:1637](../../src/ahp/host.ts#L1637)). A channel is unresolvable when its session is gone or no longer the person's ([host.ts:1486](../../src/ahp/host.ts#L1486)).

**(source)** The composer of a new session creates a provisional session on the host and holds a subscription to it and to its default chat for as long as it is open. The comment in the client says why: "so the agent host's empty-session GC sees a non-zero subscriber count" (`workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:4296-4318`). Unfold keeps provisional sessions in a map in memory ([host.ts:279](../../src/ahp/host.ts#L279)), so a restart of the host loses them while the client keeps asking for them.

**(probe)** Against Unfold's host at `313b045f`: a client initialized, created a provisional session, subscribed to it and to its chat, and closed. After a restart, a `reconnect` naming the root channel and those two channels was answered with `-32001`, "Unfold has no such session, or it is not yours. Reopen it from the Unfold view.", for the whole request. An `initialize` with the same three channels got the same error. A `reconnect` naming only the root channel succeeded.

The same failure follows any channel that stops resolving while a client is away: a session another window deleted, a Team the person left, and a Work Item channel while Ploeg cannot be read. How often a person has such a composer open on Unfold at the moment of a restart is not measured.

AHP gives a replay result a `missing` list for exactly this case and gives a snapshot result none ([`types/common/commands.ts`](https://github.com/microsoft/agent-host-protocol/blob/main/types/common/commands.ts), `ReconnectReplayResult.missing` and `ReconnectSnapshotResult`). Unfold always answers with snapshots. The candidate fixes, none chosen:

- leave a channel that does not resolve out of the snapshots of `initialize` and `reconnect`, and tell the client that the session is gone with `root/sessionRemoved`. After a fresh `initialize` the client re-subscribes each channel the snapshots left out on its own and marks only that one as failed (`agentHostProtocolClient.ts:1443-1452`, `:1466-1519`). After an ordinary `reconnect` it does not, so the removal notice is what tells it;
- keep provisional sessions in the store, so a restart loses none. They already have a limit of 20 per person and an expiry of 24 hours;
- both.

Since 1.148 the client also drops, after a reconnect, the queued actions of a channel whose subscription is in error, where 1.147 sent them (`agentHostProtocolClient.ts:1956-1961`). Once the fix is in, a message typed into a vanished session during a reconnect disappears without a rejection, so the removal notice matters for that case too.

### Paging through `fetchTurns`

**(source)** At 1.147.0 no client code called `fetchTurns`. At 1.148.0 the session handler exposes `loadOlderHistory`, which calls it with the chat's `turnsNextCursor` (`workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:826-838`, `:2122`). The chat list calls it when a person scrolls near the top (`workbench/contrib/chat/browser/widget/chatListWidget.ts:1336-1362`) and Find calls it to search the whole chat, reporting an incomplete search when turns are missing (`workbench/contrib/chat/browser/widget/chatFind/chatFindWidget.ts:609-660`). No setting and no capability gates it. VS Code's own host answers by dispatching `chat/turnsLoaded` with the older turns and a new or cleared cursor before it returns.

**(source)** AHP has required exactly that since 1.0.0: the host must dispatch `chat/turnsLoaded` and update or clear the cursor before it answers, and must reject a cursor it does not know. Unfold publishes the cursor on a history cut at 200 turns ([host.ts:843-845](../../src/ahp/host.ts#L843)) and answers `{}` ([host.ts:1652](../../src/ahp/host.ts#L1652)), and a test pins the empty answer ([ahp-continuity.test.ts:156-177](../../test/ahp-continuity.test.ts#L156)). The cursor was a hint in 1.147, which read it as "there is more" and never asked.

The effect is limited to a chat of more than 200 turns. There, older turns never load, each scroll to the top sends a request that changes nothing, and Find says the search is incomplete. Restoring a checkpoint or editing the first loaded message throws "The chat history changed before the checkpoint could be restored. Reopen the chat and try again." in place of Unfold's own sentence about why a transcript is kept (`agentHostSessionHandler.ts:3955-3979`). No message fails to send.

On AHP's `main`, [#620](https://github.com/microsoft/agent-host-protocol/pull/620) marks this paging as legacy and adds deferred turns: a client that declares `capabilities.deferredTurns` gets every turn, with the older ones as headers whose content it fetches on demand. That suits a transcript that is evidence better than a tail window does. 1.148 does not vendor it, and the paging "remains supported for 1.x clients that do not declare `deferredTurns`".

### A host that an extension registers

**(source)** `vscode.proposed.remoteAgentHost.d.ts` did not exist at 1.147.0. It declares `chat.registerRemoteAgentHost({ name, address, connectionToken? })`, which returns a disposable. A registration lives per window, in memory, one per normalised address; nothing is written to settings and nothing is synced (`platform/agentHost/common/extensionRemoteAgentHosts.ts:80-133`). The same WebSocket factory dials it as dials a `chat.remoteAgentHosts` entry.

What changes for a host registered this way, compared with a settings entry:

- **Remote Environments.** It gets a row under Extensions, "Registered by the … extension", with Connect, New Session, Rename, Show or Hide in the picker, Troubleshoot Connection and a link to the extension. A settings entry gets no row at all and is managed only from the environment picker (`workbench/contrib/sessions/providers/remoteAgentHost/browser/remotesModel.ts:50`, `:1415-1487`).
- **Editor windows.** Each editor window connects to the hosts its own extensions registered, and their agents and sessions appear in Chat, as for `chat.workspaceRemoteAgentHosts` (`workbench/contrib/chat/browser/remoteAgentHost/editorExtensionRemoteAgentHosts.ts:14-41`). The host sees one more connection per editor window, with the client name `vscode-editor-window`.
- **Disconnect.** A person can disconnect, rename and hide the host and cannot remove it. A disconnect is remembered by address in application storage, and the API gives the extension no status and no event (`extensionRemoteAgentHosts.ts:61`, `:117-133`).

Unfold Insiders already calls it ([extension.ts:823-849](../../extensions/vscode/src/extension.ts#L823)). On 1.147 the name was unknown, so the extension fell back to writing `chat.remoteAgentHosts`. On 1.148 the registration succeeds and the method returns before the settings path. Four things follow:

- A settings entry written earlier, with its token, is not removed when registration succeeds; only signing out removes it ([extension.ts:1016-1019](../../extensions/vscode/src/extension.ts#L1016)). On the machine this was checked on, the Insiders profile holds no such entry.
- In the Sessions list of an editor window that has folders, the rows are hidden. That list is behind `chat.viewSessions.sessionsList.enabled`, which is off by default. Its scope rule changed in 1.148: a session of another host never matches a local folder, and a session without a workspace is in no scope where 1.147 put it in every scope (`workbench/contrib/sessions/browser/sessionScope.ts:84-99`). A session whose folder is a `github-remote-file://github/<owner>/<repo>` address is in the scope of a window whose folder's origin is that GitHub repository (`sessionScope.ts:15-21`).
- The row and its Troubleshoot page describe Unfold as a machine: "Update required", "Server update: Not available over this connection", and for sandbox profiles "The server on Unfold doesn't support sandbox profiles yet. It needs a newer server version." (`remotesTable.ts:306-307`, `:577-583`; `remoteTroubleshooting.ts:99-108`). The page names the server as `unfold live`, from the host's `serverInfo` ([host.ts:1625](../../src/ahp/host.ts#L1625)).
- A rejected token still reads as a transport failure, "WebSocket connection failed", with advice to check the extension. Upstream draft U2 stands.

The API offers no sign-in state, label, icon or action, and nothing of it works without the proposal, so the regular extension keeps writing the setting.

### Remote Environments and the diagnostic report

**(source)** Opening the editor sends nothing to a connected host. Its cells come from state the client already holds: status from the connection, last activity from the newest `modifiedAt` of the host's sessions, and the system column from `_meta['vscode.agentHost.resources']` on the root state, which Unfold does not publish, so the cell stays empty (`remotesModel.ts:1357-1392`).

**(source)** The Troubleshoot page runs no probe of its own. Its Copy Report and Open Diagnostic Report list every environment, not only the one being looked at: name, address without its query, type, status, protocol client id, the last connection step and its error, the advertised agents, and up to 200 lines of the window log (`workbench/contrib/sessions/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts:239-414`). The connection token is not in it: it is added only when dialling, and bearer values, `tkn=` and token-shaped strings are redacted. The address of an Unfold installation is in it, so a person who shares a report about another host shares that address too.

The claim in the notes that responses begin 30% faster is about VS Code's own host: a provisional session is kept warm while a person composes, and the provider may wait for the turn's checkpoint itself. For a direct WebSocket host nothing changed between pressing send and the dispatch of the turn.

### Remote sessions started by an agent

**(source)** With `chat.agentHost.devContainer.handoff.enabled`, which is off by default, the client publishes the tool set `vscode-remote-sessions` to every agent-host session: `list_agent_hosts`, `create_dev_container`, `create_remote_session`, `get_remote_session` and `send_remote_message`. A target host is refused with "Host does not support remote session delegation. Update the agent host." unless its root state carries `_meta['vscode.remoteSessions']` (`platform/agentHost/common/meta/vscode/agentRemoteSessionMeta.ts:14-27`; `sessions/contrib/remoteSessions/common/remoteSessions.ts:193-204`). VS Code's own host always sets it. Unfold's root state has no `_meta` at all, so no agent can start or message a session on Unfold this way. The 2026-10-01 rule holds: Unfold does not advertise the key until delegation can only create proposals. No test pins the absence.

### Native visuals

**(source)** Both settings are plain defaults now, `true`, and their descriptions still say that a client with them off shows the block as source code (`workbench/contrib/chat/browser/chat.shared.contribution.ts:1997-2007`). The components and limits are as the 1.147 dossier recorded them.

The host sees `clientInfo: { name, title }`, with the names `vscode-agents-window` and `vscode-editor-window`, and an `initialize` `_meta` of telemetry and capability keys; none carries a version (`platform/agentHost/common/agentHostClientInfo.ts:17-25`; `agentHostProtocolClient.ts:1696-1710`). Three ways to decide, none chosen: send visuals to every VS Code client and accept source code on 1.147 and on clients that turned the setting off; let the extension report the VS Code version and the two settings for its window, which leaves out people who connect without the extension; or read the root key `keepAwakeWhileWorking`, which a client mirrors at connect only since 1.148, as the mark of a 1.148 client.

### MCP Apps in fullscreen

**(source)** The host context now offers `availableDisplayModes: ['inline', 'fullscreen']`, the current `displayMode` and `containerDimensions`. A view that declares no display modes may be switched to either; a view whose declared list lacks `fullscreen` gets no button, and its `ui/request-display-mode` is answered with the mode it already has (`workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts:108-116`, `:776-784`, `:834-842`). Fullscreen is a read-only editor tab titled from `appInfo.title` or `appInfo.name`; the same frame moves without a reload, and scroll-wheel forwarding is off there, so the view scrolls itself. VS Code's own documentation still says "`inline` only".

Unfold's view declares `availableDisplayModes: ['inline']` and `appInfo.name: 'unfold-view'`, reads only the theme from the host context, and has no maximum width ([view.js:5](../../public/mcp-apps/view.js#L5), [view.css](../../public/mcp-apps/view.css)). So nothing changes today. Dropping the declaration alone would put the card at the top left of a large pane under the tab title `unfold-view`.

One change does reach the card unasked: an MCP App's document now gets `body { padding: 0 }`, where the webview default of 20 pixels left and right applied before (`chatMcpAppModel.ts:691-695`). The card sets no body padding of its own, so it sits 40 pixels wider, flush with the chat column.

### Sign-in, the ID token and `authenticate`

**(source)** 1.148 moved the account hint of `authenticate` from `_meta['vscode.authentication.account']` to the top-level `accountId`, with no compatibility bridge ([#347244](https://github.com/microsoft/vscode/pull/347244)). The client sends `authenticate` only for a protected resource a host advertised, and Unfold advertises none ([host.ts:722](../../src/ahp/host.ts#L722)), so none of it arrives.

On VS Code's `main`, [#350464](https://github.com/microsoft/vscode/pull/350464) forwards the OpenID Connect ID token of the sign-in as `authenticate.idToken` to every host that gets an `authenticate`, following AHP [#631](https://github.com/microsoft/agent-host-protocol/pull/631). The AHP pull request names the open point itself: "a client that supports the field sends identity claims to every host". Unfold's host answers `authenticate` with `{}` for any resource ([host.ts:1668](../../src/ahp/host.ts#L1668)), while AHP requires an error for a resource the host did not advertise. Nothing is stored or logged today. Answering with an error keeps the host out of the path of tokens it never asked for, before 1.149 ships on or about 2026-12-02.

### U6. List WebSocket hosts from `chat.remoteAgentHosts` in Remote Environments

> The Remote Environments editor builds its rows from SSH, WSL, tunnel, GitHub Environment, extension and Dev Container entries (`remotesModel.ts:50`, `:1415-1487`). A host a person added with Add Remote Agent Host, the route the AHP blog post describes for third-party hosts, has no row, no status and no Troubleshoot Connection, and is managed only from the environment picker. List those entries too.

### U7. Do not describe every remote agent host as a VS Code server

> For an extension-registered host the Remote Environments row and the Troubleshoot page say "Update required", "Server update: Not available over this connection" and "The server on {name} doesn't support sandbox profiles yet. It needs a newer server version." (`remotesTable.ts:306-307`, `:577-583`; `remoteTroubleshooting.ts:99-108`). A third-party host is a product with its own releases. Show these lines only for hosts that advertise `vscode.build`, and otherwise say that the host does not offer the feature.

### U8. Give `chat.registerRemoteAgentHost` a status and a way back from Disconnect

> A person's Disconnect of an extension-registered host is stored by address (`extensionRemoteAgentHosts.ts:61`, `:117-133`) and the registering extension learns nothing: it has no connection status, no event and no way to offer Reconnect. A rejected token is a transport failure. Add a status and a change event to the returned registration, and let the extension supply a fresh token on an authentication failure.

### U9. A snapshot reconnect has no way to name a channel the host cannot resume

For [microsoft/agent-host-protocol](https://github.com/microsoft/agent-host-protocol/issues).

> `ReconnectReplayResult` has `missing` for subscriptions the host cannot resume; `ReconnectSnapshotResult` has only `snapshots` (`types/common/commands.ts`). A host that always answers with snapshots can either fail the whole command, which makes VS Code retry ten times and then close, or leave the channel out, which a client notices only after a fresh `initialize`. Add `missing` to the snapshot result, with the same meaning.
